## 5. Findings
### BUG-01 (major) — `pnpm typecheck` fails in `@mytask/api`; CI would be red
- **Where:** `apps/api/test/content-language.test.ts:10-14` imports `englishFieldIssue`, `georgianFieldIssue`, `normaliseContentText` from `@mytask/i18n`. That package's entry is TypeScript source with `"type": "module"` (`packages/i18n/package.json`). The API compiles as CommonJS with `module`/`moduleResolution` `Node16` (`apps/api/tsconfig.json`).
- **Since:** 4.3.9 `90d93305` (the client/server parity test of the content-language rules).
- **Steps:** `pnpm --filter @mytask/api typecheck` (or `pnpm typecheck`).
- **Expected:** 0 errors. **Actual:**
  ```
  test/content-language.test.ts(14,8): error TS1479: The current file is a CommonJS module whose imports will produce 'require' calls; however, the referenced file is an ECMAScript module …
  ../../packages/i18n/src/index.ts(73,8): error TS2835: Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './content-language.js'?
  ```
- **Impact:**
  - CI (`.github/workflows/ci.yml:106` `pnpm typecheck`) fails, so the 4.3.21 PR cannot go green.
  - Turborepo stops at the first failed task, so a plain `pnpm turbo run lint typecheck test` stops before the API tests and hides their result.
  - Vitest still runs the test (it transpiles without type checks), so the API test suite stays green.
  - Product code is not affected: the API `src` imports only the i18n JSON files.
- **Owner:** web engineer (author of 4.3.9) with backend, in 4.3.20.
  - Make the parity test type-check under the API's settings without changing product behaviour. One way is to import the shared helpers in a form the API's Node16 resolution accepts. Another is to move the parity check where ESM is native.
  - Then run `pnpm typecheck` **at the root** before each handoff.
