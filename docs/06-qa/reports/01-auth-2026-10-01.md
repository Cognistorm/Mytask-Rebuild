## 3. Findings (part 1)
| ID | Severity | Area | Finding | Evidence | Owner of the fix |
|---|---|---|---|---|---|
| F-01 | minor (doc / decision) | AC-18, R-A10 | Spec 01 R-A10 says the mobile app uses Google's mobile reCAPTCHA SDK and that "the exact mechanism is decided in ADR-002"; ADR-002 says "mobile relies on throttling and may use reCAPTCHA Enterprise / App Check later (**spec 01 decides**)". Each document defers to the other, and the API checks reCAPTCHA on web only, so AC-18 ("register or login without a valid token is refused") does not hold for the app when S-061 is ON. No effect at launch (S-061 launch value OFF, R-A10), but the rule is undecided. | QA-REC-1; `apps/api/src/modules/auth/recaptcha.service.ts:1-2`; ADR-002 line 55 | solution-architect + product-analyst (align ADR-002 and R-A10; Owner if a mobile check is wanted) |
| F-02 | minor (test) | web E2E | The routed tests in `apps/web/e2e/sessions.spec.ts` answer `listMySessions` by **call count** (`lists[n]`). On a dev server React StrictMode mounts twice, the second call gets the post-revoke list, and "list (en)" and "wrong current password (ka)" fail. The committed config uses `pnpm start`, where they pass, but `PW_REUSE=1` against `pnpm dev` (documented for local runs, BUG-07) gives false failures. | A-11; `sessions.spec.ts:66-100` | web-engineer: answer by state (e.g. return the post-revoke list only after a revoke call) |
| F-03 | minor (UX, check on screen in 3.15b) | AC-22, AC-27 | A 2FA user who submits the login form again within 60 s of the previous code (e.g. goes back from the code step, or logs in on a second device) gets `429 TWO_FACTOR_RESEND_THROTTLED` **on the login call**, after a correct password. This matches the 60-second rule, but 3.15b must check that web and app show `t_2fa_resend_wait` with the seconds rather than a generic error. | QA-2FA-6 needed a cooldown reset before the second login; `two-factor.service.ts:115-117` | web/mobile (if the screen shows a generic error) |
| D-1 | deferred (tracking) | AC-6, AC-7, EC-1 | Referral crediting at activation is a documented no-op until slice 09 (`referral.service.ts` `creditSignup`); the pending row is stored correctly. ROADMAP slice 09 had no task naming it, so QA added it to 4.8.6. | QA-VER-1; `referral.service.ts:1-5,31-33` | slice 09 (ROADMAP 4.8.6) |
