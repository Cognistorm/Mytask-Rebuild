## 3. Findings — Medium

### SEC-33 (Medium) Open redirect after login through `?next=`
- **Where:** `apps/web/src/app/[locale]/auth/login/page.tsx:44` — after a successful login or 2FA code the page calls `router.push(search.get('next') ?? …)` with the raw query value.
- **Exploit (in words):** an attacker mails a real MyTask link such as the login page with `next` set to an absolute URL on a look-alike domain (or a protocol-relative `//host`). The victim sees the genuine site, signs in (the trust signal is real), and is then sent by the Next.js router (it performs a full navigation for external URLs) to the attacker's page, which can say "session expired, enter your password again" or "enter the code we just emailed", harvesting credentials or a live 2FA code. url-map.md line 68 plans the same `next` parameter for the register page, so the pattern will spread.
- **Fix:** accept `next` only when it is a same-site relative path: it must start with a single `/`, must not start with `//` or `/\`, must not contain a scheme, backslash or control characters; parse it with `new URL(next, location.origin)` and require `url.origin === location.origin`; otherwise use the default. Put this in one helper in `apps/web/src/lib/client.ts` and use it on every page that honours `next` (login now; register per url-map §3). Add a Playwright test with an absolute and a `//` value. **Owner:** web-engineer.

### SEC-34 (Medium) Throttles are check-then-act: parallel requests bypass the S-062 lock, the per-challenge limit S-058, the SEC-03 code cap and the SEC-04 in-session lock
- **Where:**
  - Login: `auth.service.ts:221` reads the lock and the per-account counter (`throttle.service.ts:57-69`), then the Argon2 check runs (tens of ms), and only then `loginFailed` increments (`throttle.service.ts:72-85`).
  - 2FA code: `two-factor.service.ts:168-176` reads the account lock and `challenge.attempts`, compares the code, then writes `attempts: challenge.attempts + 1` as an absolute value (`:182-187`) and increments the Redis cap (`:188`).
  - In-session: `account.service.ts:172-178` reads the lock, verifies, then increments.
- **Exploit (in words):** a caller sends a burst of many requests at the same moment. Every request passes the "is it locked?" check before any of them has recorded its failure. For 2FA, every request also reads `attempts = 0` and writes `attempts = 1`, so the per-challenge limit of 5 never triggers, and the 10/hour account cap is only set after the whole burst has already been evaluated. Someone who already has the password (phishing, reuse from another breach) can therefore try hundreds of codes per burst instead of 10 per hour, repeat after each S-063 lock, and reach a meaningful chance of passing 2FA within a day — the protection SEC-03 was designed to give is lost. The same burst defeats the per-account + IP lock (S-062) and lets many passwords be tried before slow mode starts each hour.
- **Fix:** reserve before checking, atomically.
  - Redis: increment an "attempts" counter (or run one Lua script) **before** evaluating; refuse when the value after the increment exceeds the limit; for login, reset on success as today. The slow-mode slot already uses `SET NX` correctly — keep it.
  - Challenge: replace the read-then-write with a conditional update that increments only while under the limit (`attempts < max_attempts`, `consumed_at IS NULL`, `invalidated_at IS NULL`, `expires_at > now()`), and only compare the code when that update affected one row.
  - Add concurrency tests (e.g. 30 parallel wrong codes must leave at most S-058 evaluated and must trigger the cap). **Owner:** backend-engineer.

### SEC-35 (Medium) The contract's global per-IP limits are not implemented
- **Where:** CONVENTIONS §14 "Global defaults … 600 requests/min per user or IP for reads, 120/min for writes"; the contract declares "global write limit per IP" on `register` (`docs/04-api/src/paths/d1-platform-auth-profiles.yaml:153`), `login` (`:211`), `verifyTwoFactorLogin` (`:259`), the email operations (`:425`, `:459`) and the in-session operations. No rate-limit middleware or guard exists in `apps/api/src` (the only limits are the per-account ones in `throttle.service.ts`).
- **Exploit (in words):** (1) password spraying / credential stuffing — one IP tries 4 passwords on each of thousands of accounts; each account stays below S-062 and below slow mode, so nothing stops it. (2) `register` has no limit at all while reCAPTCHA S-061 is OFF by default (`platform/settings/settings.service.ts:15`) and is never checked for `ios`/`android` (any caller can send that header): mass fake accounts; with S-053 = `admin`, every pending registration queues EV-02 to the admin address (S-100), an easy email flood of the Owner's inbox. (3) The resend endpoints and `password-reset/validate` can be hammered for load.
- **Fix:** add the global limiter in the platform layer (Redis, keyed by `ClientIpResolver` IP for anonymous calls and by user id when authenticated, IPv6 by /64 — see SEC-42), 429 `RATE_LIMITED` with `Retry-After`, exactly as §14 states; add a specific limit for `register` per IP (e.g. 5 per hour, spec to confirm) and cap EV-02 per hour. Tests for each declared `x-rate-limit`. **Owner:** backend-engineer (platform); product-analyst to confirm the register number.

### SEC-36 (Medium) Worker prints reset links and 2FA codes to the log when `SMTP_URL` is missing — the production guard can be bypassed
- **Where:** `apps/api/src/worker/outbox.dispatcher.ts:36-38` creates a transport only when `MAIL_TRANSPORT === 'smtp' && SMTP_URL`; `:117-120` falls back to printing the full email (subject + text with the link or code) whenever `!this.transport`, then scrubs the row as "sent". `platform/config/env.ts:50` makes `SMTP_URL` optional and `:68-74` refuses only the explicit `MAIL_TRANSPORT=log` in production.
- **Exploit (in words):** a production `.env` that forgets `SMTP_URL` (or a typo in its name) starts without error. From then on every password-reset link, email-verification link and 2FA code is written in clear text to the worker's stdout — the Docker log, any log shipper, error tracking, and (ADR-013 §3) possibly the admin log page. Anyone with log access can reset any account's password or complete a 2FA login; real users silently receive nothing. The redaction list does not help because the secret is inside the message string.
- **Fix:** in `env.ts`, require `SMTP_URL` when `MAIL_TRANSPORT = smtp` (at least in production, ideally always); in the dispatcher, treat "no transport" as a delivery failure (retry, never print); in `log` mode, print the email but mask `code`/`token` unless `NODE_ENV=development`. Add env tests for `memory://`, `MAIL_TRANSPORT=log` and missing `SMTP_URL` in production (only `STAFF_BODY_TOKENS_ENABLED` is tested today, `apps/api/test/env.test.ts:36`). **Owner:** backend-engineer.

## 5. Info (no action needed now, or Phase 6 notes)
- **I-1 Caddy header stripping works** (section 1.3): the wildcard deletions are prefix, case-insensitive; `header_up -X-Forwarded-For/-Proto/-Host` removes the headers Caddy's proxy adds itself; `X-MyTask-Client-IP` is then set from `{client_ip}` (TCP peer locally). The public host refuses `/api/v1/admin/*` (Caddy path matching is case-insensitive). **Phase 6 note:** `request_header -CF-*` runs before the proxy, so a later `header_up X-MyTask-Client-Country {http.request.header.CF-IPCountry}` would read an already deleted header and be empty. Capture the country first (e.g. with `map`/`vars` before the deletion) when adding the Cloudflare config; `client_ip` itself is computed before handlers and is not affected.
- **I-2** `ClientIpResolver` accepts the visitor headers from any non-Caddy peer that holds the credential; the "(b) internal app network" part of ADR-013 §17 is enforced only by the Docker network layout. Acceptable. `INTERNAL_SERVICE_TOKEN` is checked for length (43 chars), not entropy; `pnpm setup:env` generates 256 bits, fine.
- **I-3** `validateSecurity: false` is correct (the guard denies by default), but nothing checks that each operation with `security: []` in the contract is exactly the set of `@Public()` handlers. Add a test that walks the Nest routes and the contract and compares them, so a forgotten `@Public()` or an extra one is caught.
- **I-4** The CSRF middleware chooses the admin origin with a case-sensitive `startsWith('/api/v1/admin/')` (`csrf.middleware.ts:35`), while Express routing is case-insensitive. Harmless today (no admin routes; Caddy blocks the path on the public host); lower-case the path when admin routes arrive.
- **I-5** A login challenge stores the device hash (`two_factor_challenges.device_id_hash`) but `verifyTwoFactorLogin` does not compare it (`auth.service.ts:276-278`). Acceptable (the code proves the mailbox); compare it if cheap.
- **I-6** Locally the API and migrations connect as the Postgres superuser and Redis has no password (bound to 127.0.0.1). Phase 6: a least-privilege app role (no DDL, no superuser), a separate migration role, Redis `requirepass`/ACL on a private network.
- **I-7** `apps/mobile/app.config.ts:57-58` loads the whole root `.env` into the Metro/Expo process; only `EXPO_PUBLIC_*` values are inlined into the bundle and `extra` holds only the API URL, so no secret ships today. Keep `extra` minimal; production builds must use an https API URL. SecureStore keys `mt_access`/`mt_refresh`/`mt_device` use the default Keychain/Keystore accessibility (after first unlock/while unlocked) — fine; web never receives tokens in JS (bodies carry `null`).
- **I-8** `.env.example` lacks `MAIL_TRANSPORT` (read by `env.ts:52`); ADR-013 §8 wants every name listed.
- **I-9** `pnpm audit --prod`: 3 moderate, all in the mobile toolchain (`yaml` GHSA-48c2-rrv3-qjmp via Expo/Metro, `uuid` GHSA-w5hq-g745-h8pq via Expo config plugins, `decode-uri-component` GHSA-vcc3-ghjq-m6fr via `expo-router`/`query-string`).
