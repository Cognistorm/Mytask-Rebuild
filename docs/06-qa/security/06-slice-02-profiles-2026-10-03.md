## 3. New findings — Medium

### SEC-62 (Medium) `pnpm local`: the SeaweedFS filer serves, lists and accepts writes to every bucket (incl. `kyc`) without authentication, with `Access-Control-Allow-Origin: *`
- **Where:** `scripts/local.mjs:184-200` (`weed server … -s3 …` without `-filer.disableHttp` and without a `security.toml`); `scripts/local.mjs:51` (8888, 8334 and 9333 belong to the stack). The S3 identities of `:170-182` protect only port 8333.
- **Exploit (in words):** probe P2. While `pnpm local` runs, anyone who can reach `127.0.0.1:8888` reads any object of any bucket by path and lists directories, bypassing the S3 identity rules completely: KYC ID photos and selfies, private appeal files, everything. Because the filer answers `Access-Control-Allow-Origin: *`, that includes **any web page open in the Owner's browser** (a malicious ad, a compromised site) that fetches `http://localhost:8888/buckets/kyc/…`, in browsers that do not block public-to-localhost requests (Firefox; Chrome only with its newer local-network permission). The same page can overwrite public images with a "simple" multipart POST (no preflight), and the anonymous S3 URL then serves its HTML. The local data is synthetic today, but CLAUDE.md makes this machine the place where everything runs, and the Phase 5 ETL moves real KYC images through the same storage (data-model §12). The master (9333) also hands out write slots without credentials (orphan blobs only).
- **Fix:** add `-filer.disableHttp` to the `weed server` arguments (verified: S3 keeps working, the filer answers 404); protect master and volume with a `security.toml` (`[jwt.signing]` key written by `pnpm setup:env`), or at least document that 8334/9333 must stay local; add a start-up check in `pnpm local` that `http://127.0.0.1:8888/` is refused. Never run the filer HTTP API in a deployed environment. **Owner / when:** devops-engineer, **before merge**.

### SEC-63 (Medium) Virus-scan bypass for unprocessed files: the presigned POST is reusable and the worker copies the quarantine object after scanning an earlier version
- **Where:** `files.service.ts:30` (POST valid 15 minutes) and `storage.ts:104-116` (nothing makes the form single-use; P3); `file-scan.service.ts:77-80` (read + scan), `:101-106` (server-side `copy` of the same key afterwards), `:192-201` (`processing: 'none'`).
- **Exploit (in words):** for purposes stored as uploaded (`appeal_file` today; deliveries, requirement files, chat and offer attachments in later slices) the worker scans the bytes it read and then asks storage to copy whatever is under the quarantine key *now*. The uploader keeps re-posting the same form (allowed for 15 minutes, P3) with a different payload of the same declared type within the size bound. When a re-post lands between the read and the copy, an unscanned file becomes `ready` with the checksum and detected type of the clean one. The timing is loose, but the attacker can retry for 15 minutes and the window covers the whole ClamAV scan. Today the receiver is staff (appeal files); from slice 05/07 it is another user. Separately, a re-post after `ready` or `rejected` re-creates an orphan object under `quarantine/` that no sweeper removes (storage abuse up to the declared size per slot).
- **Fix:** keep the `ETag` (or version id) of the scan's `GetObject` and pass it as `CopySourceIfMatch` to `copy` (P5: enforced by SeaweedFS; supported by R2/S3); on `PreconditionFailed` reject the file (`t_file_rejected_unreadable`) or re-queue it. Alternatively write the scanned bytes yourself (the worker already buffers images). Shorten the POST expiry to what a large upload needs (e.g. 5–10 minutes), and let the pending/rejected cleanup also delete `quarantine/<key>` of rows that are no longer `pending`. Add a test with the in-memory storage that swaps the object between read and copy. **Owner / when:** backend-engineer, **before merge** (F0 is the base of every later file purpose).

### SEC-64 (Medium) Public images are published before they are attached or approved: free anonymous image hosting and a moderation bypass
- **Where:** `purposes.ts:79-98` (`avatar` and `portfolio_image` → `public_media`); `file-scan.service.ts:226-253` (variants written to the anonymous bucket at scan time); `files.service.ts:375` (`File.image` returns the CDN URLs to the uploader at once); `worker/files-scan.sweeper.ts:100-126` (only `pending` rows are ever cleaned); S-071 default `false` (moderation on, `registry.ts:875-887`). ADR-009 §2 says `public-media` holds "portfolio **after approval**".
- **Exploit (in words):** any signed-in user uploads `portfolio_image` files (60 per 10 minutes, S-090 = 5 MB each) and never attaches them, or attaches them to an item that stays pending or is rejected. Each upload is re-encoded to WebP up to 1,600 px and is immediately readable by anyone at a permanent, cache-forever (`immutable`) URL on the platform's media domain. Nothing removes ready-but-unattached files, and rejecting an item does not unpublish its images. The CDN becomes an anonymous image host under the MyTask name, and content that staff rejected (or never saw) stays online. For illegal imagery that is a legal and reputational risk for the platform; the unguessable file names do not help, because the uploader shares the link.
- **Fix (the architect decides the shape; ADR-009 amendment):** process `public_image` purposes into the `private` bucket (or a non-anonymous prefix) and **publish** the variants to `public-media` only when they become public: the avatar on `putMyAvatar`, portfolio images when the item becomes `active` (at once with S-071 ON, on approval otherwise). The owner and staff see unpublished images through short signed links; unpublish on reject and remove. **Stop-gap before merge:** a sweeper that deletes `ready` `avatar` / `portfolio_image` files not attached within 24 hours (the same rule as `pending`), so unattached uploads cannot serve as hosting. **Owner / when:** solution-architect + backend-engineer; stop-gap **before merge**, publish-on-approval before Phase 5 (first real users).

### SEC-65 (Medium) SSR visitor-IP forwarding is never active: Caddy does not give the web server the client IP, so all server-rendered profile traffic shares one rate-limit bucket (SEC-49 is now live)
- **Where:** `infra/caddy/Caddyfile:53-54` (`reverse_proxy web:3100` without a `header_up X-MyTask-Client-IP` line; the `edge_headers` snippet strips any client copy, `:19`); `apps/web/src/lib/api.ts:33-38` (forwards only when that header is present); `apps/api/src/platform/rate-limit/rate-limit.middleware.ts:37` (key = IP only, no user key); `components/profile/data.ts:24-49` (each profile view = 2 API reads from the web container).
- **Exploit (in words):** the header `viewerApi` waits for is set only on the API upstream, so the web server never learns the visitor IP and never sends `X-MyTask-Visitor-IP`. Every SSR call comes from the web container's address and shares its 600 reads per minute. About 300 profile or portfolio page views per minute site-wide (one person with a reload loop is enough) put every visitor's profile page into 429; the page then throws (`failed()`) and shows an error. This is the SEC-49 scenario, whose condition was "before the first slice that fetches data during SSR".
- **Fix:** set the canonical client-IP header (`X-MyTask-Client-IP` from Caddy's client_ip placeholder) on the `web` and `admin` `reverse_proxy` blocks as well (ADR-013 §15); add a test that SSR calls of two visitors land in different buckets (API test with two `X-MyTask-Visitor-IP` values and the service credential) and a CI step through Caddy that loads a profile page; then complete SEC-49 (key authenticated calls by user id, ADR-013 §17). **Owner / when:** devops-engineer (Caddy + CI) **before merge**; backend-engineer (per-user keying) before Phase 6 as already scheduled.

### SEC-66 (Medium, Owner decision) Account deletion leaves the user's images public and keeps ID documents without limit (QA N-4)
- **Where:** `account-settings.service.ts:233-248` (`deleteMe` changes only `deletedAt`, sessions and tokens); avatar and portfolio variants stay in `public-media` with `Cache-Control: immutable` (`file-scan.service.ts:33, 236-242`); KYC documents attached to any verification can never be deleted by the user (`kyc.service.ts:66-68` → `deleteFile` 409) and have no retention (SEC-12 / Q-147 open).
- **Exploit (in words):** after a user deletes the account the profile answers 404, but the user's face (avatar) and portfolio images stay downloadable by anyone, without limit, at URLs that were embedded in public pages, shared links, search-engine image indexes and CDN caches. ID photos and the selfie (also of declined submissions) stay in `kyc` indefinitely. Under the Georgian Law on Personal Data Protection (storage limitation, erasure on request) and GDPR-style principles this is personal data kept and published without a purpose after the user withdrew. Soft delete matches legacy (AC-34), so the Owner must decide what "delete" means for data.
- **Fix (recommendation for the Owner):** on `deleteMe`, delete (or move to `private`) the public variants of the avatar and of every portfolio item; keep the rows if staff must still see them. KYC: implement the Q-147 proposal (delete images N days after the decision and at account deletion unless a legal hold applies; keep the decision record). Profile texts and linked accounts of deleted accounts: pseudonymise after the retention period (Q-147). Document the erasure procedure. **Owner / when:** Owner decision (Q-147 + this item); backend-engineer removes the public variants **before Phase 5** at the latest (recommended as a slice 02 follow-up); KYC retention before the Phase 5 KYC import.

## 5. Info
- **I-30 (QA N-1) Validation before authentication: accepted.** The contract validator is an early `app.use` (`app.setup.ts:54-55`) and Nest guards run after it, so a guest gets `400` field errors before `401`. The schemas are public (`openapi.yaml`), the limiter already counts these requests (SEC-50), and no handler or database work runs. ADR-002 §2 fixes only the CSRF-before-content-type order; this order is consistent with it. No change; the architect may add one sentence to ADR-002 §2 ("contract validation precedes authentication; it reveals only public schema information").
- **I-31 (QA N-2) The report limit is counted before the target check: intended, write it down.** `profiles.service.ts:294` counts every attempt, including 404 (unknown user), 403 (own profile) and blank reasons. This is the safer order (probing and spamming cost the same as reporting) and matches SEC-23 ("10 reports per user per hour"). Add "every attempt counts" to the contract `x-rate-limit` text of `createUserReport`.
- **I-32 Legacy URLs at import.** `http(s)`-only is enforced by the API (`profile-lists.service.ts:45-52`, `portfolio.service.ts:643-650`), but web, admin and mobile use the API value as `href` / `Linking.openURL` without their own scheme check (`portfolio/[slug]/page.tsx:86-91`, `profile/[username]/page.tsx:186`, `admin/app/portfolio/page.tsx:83-88`, mobile `profile/[username]/index.tsx:252`, `portfolio/[slug].tsx:114, 121`). The Phase 5 ETL must apply the same rule to legacy linked accounts and portfolio links (drop anything not `http(s)`), or the clients add a one-line guard. The provider links may point to any host (no host check, legacy parity).
- **I-33 Image decode cost.** `limitInputPixels: 100_000_000` (`file-scan.service.ts:32`) lets a 2 MB PNG avatar decode to about 400 MB, four times (metadata + three variants), and one user may queue 60 per 10 minutes. Consider a lower pixel limit for avatars and portfolio images (e.g. 40 MP), `sequentialRead: true`, and at most N `scanning` files per user.
- **I-34 (QA N-5) Queues show items of deleted accounts.** Staff can approve a pending item or verification of a deleted user, which queues EV-15 / EV-17 to that account. Spec 16 check; with SEC-64/SEC-66 such an approval must not republish images.
- **I-35 The admin CSP (SEC-48) gains weight.** The admin app now renders user-written portfolio text, links and KYC owner data and shows signed KYC images, still without any CSP. React escaping protects it today; the Phase 6 admin CSP must allow the storage origin in `img-src`.
- **I-36 The new audit highs are build tooling only.** `node-forge` (via `@expo/cli`) and `braces` (via `@next/eslint-plugin-next`, `metro`) have no patched version and do not ship in the API, worker or web server. Track with I-9; re-run `pnpm audit --prod` before Phase 6.
- **I-37 Presence is public (parity).** `isOnline` is shown to anyone for every profile and summary (R-P4, legacy), so activity patterns can be observed by polling. One Redis `SET NX` per authenticated request is cheap. No action unless the Owner wants an "appear offline" option.
