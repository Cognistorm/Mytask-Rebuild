## 3. New findings — Medium

### SEC-57 (Medium) Staff login IP ban (S-064) can be bypassed: parallel burst, reset by any password-only success, full-address key
- **Where:** `apps/api/src/modules/staff/staff-auth.service.ts:57` (ban read) → `:78-82` (Argon2 check) → `:84` and `:314-333` (failure recorded afterwards); `:87-90` (counter reset on a correct password, **before** the 2FA step at `:98`, for whichever staff account logged in); `:309, 316` (key = full client IP, no IPv6 /64); no per-account counter for staff at all (ADR-002 §6 keeps only the legacy IP rule). The platform `staff` bucket allows 1,200 requests per IP-minute on this route (review 03 SEC-50).
- **Exploit (in words):** (a) An attacker who targets the admin login sends a large burst of password guesses at the same moment. Each request checks "is this IP banned?" before any of the others has recorded its failure; Argon2 then runs on a small thread pool, so the whole burst is evaluated. Probe P1: 40 parallel guesses were all checked with S-064 = 3. With the staff bucket this is up to about 1,200 guesses per minute per IP; after the ban, the next address in the same IPv6 /64 starts a fresh counter. (b) Anyone who holds *some* staff password (a low-privilege moderator, a former employee whose account still works, a phished support agent) resets the counter of their IP every time they enter that password correctly, without even completing 2FA. Probe P2: 10 wrong guesses at another staff account, no ban. (c) There is no lock per staff account, so a guesser spread over many IPs (botnet, IPv6) is never slowed down for a given admin. With S-060 ON a correct guess yields a 2FA challenge (a confirmed password that can be reused elsewhere and combined with phishing for the code); with S-060 OFF (as set locally today, and switchable by the Owner) a correct guess is a full admin session.
- **Fix:** (1) reserve the failure *before* the password check, exactly as SEC-34 did for users: increment the IP counter atomically first (Redis `INCR`, or `UPDATE … SET failed_attempts = failed_attempts + 1 … RETURNING`), refuse when the value after the increment exceeds S-064, and give the reservation back only on a fully successful login; (2) reset the counter only after the session is issued (after 2FA when it applies) and only for the failures of the account that logged in, or not at all (legacy cleared the whole IP counter; the analyst confirms whether "success" may require a full login); (3) key the counter and the ban by `ipBucket` (/64 for IPv6), moved next to the resolver (SEC-42); (4) add a per-staff-account counter (S-062/S-063 as for users); this changes ADR-002 §6, so the architect records it first; (5) give staff **writes** the 120/min write budget (SEC-50). Tests: 30 parallel wrong staff logins → at most S-064 checked, then banned; a correct password without completed 2FA does not reset the counter. **Owner:** backend-engineer (+ solution-architect for the ADR-002 §6 note).

Role management in slice 16 (`adminCreateRole` / `adminUpdateRole`) must never let a request set or change `is_system`, and must refuse to edit or delete the system role; otherwise a staff member with `staff.manage` could grant themselves every permission.
- **I-23** `completeSocialLogin` always issues a "remember me" session (`social-auth.service.ts:197, 212`) and a new social account skips 2FA by design (`:212`, AC-38). Acceptable; fold the first point into the SEC-41 fix (carry `remember_me` on the session row).
- **I-24** The mobile PKCE challenge is accepted as any non-empty string with method S256 (`social-auth.service.ts:105`); the app generates a proper one (`expo-auth-session` `buildCodeAsync`). Optionally check the RFC 7636 shape (43 base64url characters) so a faulty client cannot start a flow with a guessable challenge.
