## 3. 4.3.24 (staff removal takes the gig's files offline)

| Question | Result |
|---|---|
| Removed gig's files really offline? | Yes. `GigMedia.sync` copies every object (main key + all image variants) to `private`, deletes the public objects, then switches `files.bucket`. Public serving reads the bucket only (`/media/` → `public-media`), so the old URL answers 404. Public mappers (`gigDocument`, `imageVariants`) also return nothing for a non-public file |
| Can the owner bring them back? | No. A deleted gig is 404 for its owner (`ownGig`); `isUsed` counts every gig including deleted ones, so the files cannot be attached to another gig (which would make the sweeper move them back public); `deleteFile` refuses a file a gig uses |
| Headers kept across the move? | Yes. `copy` without `contentType` uses `MetadataDirective: 'COPY'`, so documents keep `Content-Disposition: attachment` and variants keep their `Cache-Control` (integration test, real SeaweedFS) |
| Races and failures | `sync` and `restore` both take the gig row lock, so a move and a restore never interleave. A failed move after a removal is logged and retried by the sweeper (every 5 min, `SKIP LOCKED`). A restore copies back inside its transaction and switches the rows there, so the gig is never active with private files; on rollback the public copies are deleted again. Worst case after a storage outage: a removed gig's files stay public until the next sweeper pass |
| Staff access | Staff see private files through presigned GETs (`DOWNLOAD_EXPIRES_SECONDS`, `attachment`, `private, no-store`), the same as other private files. Only behind `gigs.moderate` |

## 4. New findings
- **I-62 (Info, Phase 6, devops):** gig image variants are stored with an immutable `Cache-Control`. On staging (no proxy cache) a removal takes them offline at once. With a CDN in front of `public-media` in production, a staff removal must also purge the gig's URLs from the CDN, or the files stay reachable there until the cache expires. Add to the SEC-80 (c) media-host set-up.
- **I-63 (Info, Phase 5, data-migration):** SEC-80 (a)+(b) apply only to files that go through the scan worker. Gig documents imported from legacy must get the same treatment (byte-0 `%PDF-` check and `Content-Disposition: attachment` with the cleaned original name), either by sending them through the worker or by setting both in the migration script.
