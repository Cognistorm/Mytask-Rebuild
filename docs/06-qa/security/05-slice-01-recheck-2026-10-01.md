## 3. New findings: Info only

- **I-25 Refresh reuse grace (SEC-44): residuals, no action now.** (a) Theft detection is suspended for 20 s after a rotation: if an attacker who stole a refresh token rotates it first and the real client refreshes within 20 s, the real client gets 401 and the family is **not** revoked, so the attacker keeps the session until it expires or the user ends it in the sessions list (`sessions.service.ts:110-113`). The attacker must win a race whose timing they do not control; reuse after 20 s still revokes. (b) The mobile "lost answer" case is not helped: the app retries with the old token, gets 401 and `clearSession()` runs (`apps/mobile/src/lib/api.ts:57`), so the user signs in again. If either matters later: within the grace hand out the already-issued successor once (bound to the same device id hash) instead of a bare 401, and on a grace hit from a **different** device id or IP bucket revoke the family as before.
- **I-26 reCAPTCHA clients are not wired yet.** The server now requires the actions `login` / `register` / `staff_login` and the exact host (SEC-47), but no web or admin page calls `grecaptcha.execute` (no reCAPTCHA code in `apps/web/src` or `apps/admin/src`). Switching S-061 ON today would refuse every web login and registration and every staff login (fail closed: availability, not security). Before S-061 is turned ON anywhere, the web and admin forms must send tokens minted with exactly these action names on APP_URL / ADMIN_URL; add this to the S-061 / Q-160 item. Any client can also claim `ios`/`android` to skip reCAPTCHA on user login and registration (known, Q-160), so S-061 alone is not a bot barrier until Q-160 (b) or (c).
- **I-27 `ipBucket` on addresses that start with `::` and have three or more further groups** returns `::/64` (probe P6: `::2:3:4:5:6:7` → `::/64`; correct is `0:0:2:3::/64`) because the expansion loop inserts the zero run twice for a leading `::` (`client-ip.resolver.ts:35-43`). Such sources are reserved / IPv4-compatible space and do not reach the API over the internet, so there is no effect today. Fix when convenient: expand from the canonical form by splitting on `::` once, and add the case to `rate-limit.test.ts:60`.
- **I-28 Manual IPv6 bans are single addresses only.** `createBan` accepts only an address (`admin-security.service.ts:38`), while automatic bans are /64 and an attacker rotates inside the /64. Slice 16 (admin IP-ban screen): accept an IPv6 /64 prefix in `adminCreateIpBan` (the lookup with `inet <<=` already supports it), and check the `q` search on the `inet` column (`:30`, `contains` on an `inet`) at the same time.
- **I-29 The EV-02 cap can be filled on purpose.** S-132 counts EV-02 emails per clock hour for all IPs together (`throttle.service.ts:229-232`), so someone registering from 20 addresses in one hour suppresses the admin email for genuine registrations in that hour. No data is lost (the users are listed as pending, as the Owner accepted in Q-159). Note for the admin guide: the pending filter is the source of truth, the email is a convenience.
