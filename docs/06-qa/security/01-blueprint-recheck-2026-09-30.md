## 3. New findings from the re-check (did the fixes introduce anything?)
Nothing the fixes introduced is High or Medium. Two new Low findings and one set of implementation notes:

| ID | Sev | Area | Location | Description | Required fix | Owner |
|---|---|---|---|---|---|---|
| SEC-30 | Low | AuthN / availability | ADR-002 §6 "Per account, any IP (SEC-02)"; `login` | In slow mode, only one password attempt per 30 s is evaluated per **account**. Anyone who knows a user's email can send an attempt every few seconds (from several IPs), use up nearly every slot, and so make the real user get `429 AUTH_LOGIN_THROTTLED` almost every time. That is a practical lock-out, which the design explicitly wanted to avoid ("no hard lock"). | Let attempts that carry a **trusted device** of that account (`__Host-mt_did` / mobile `deviceToken`, ADR-002 §5) bypass the slow-mode slot; they still count toward the per-account+IP counter. On web, an attempt with a passed reCAPTCHA may also bypass it. Then slow mode only slows unknown devices. Also state that attempts refused by slow mode or the per-account+IP lock do not consume the slot. Close in slice 01. | solution-architect (ADR-002 §6) |
| SEC-31 | Low | Availability | `handleBogWebhook` step 1 (flood hardening), ADR-004 §3 | Unknown order ids are capped (100/h), but callbacks for a **known** payment that is already final are "stored for staff" with no cap. Any user knows the BOG order id of their own paid payment (it is on the receipt, spec 05 AC-33), so they can repeat such callbacks to grow `payment_events` (60/min per IP, 600/min for everyone until BOG's ranges are confirmed). | Cap stored events per payment (e.g. store the first N per payment per hour, then only a counter), or deduplicate identical bodies by hash. Also align step 1's wording ("stored … before anything else") with the look-up-first rule. Close in slice 05. | solution-architect |
| SEC-32 | Info | Implementation notes | ADR-002 §1, §7; CONVENTIONS §19 | (a) `completeSocialLogin` must pick the binding check from the **client kind stored with `state`**, not from the callback's `X-MyTask-Client` header; a state with no stored nonce or challenge must never pass (no null = null match). (b) Slow mode and the SEC-03/SEC-04 locks can be triggered by someone who knows the password or holds a session (short denial of service). This is acceptable because password reset stays available and ends every session; keep `completePasswordReset` outside those counters. (c) Redis is now security-critical (deny-list, counters; fail closed = 503): monitor it like the database (ADR-015). (d) The sanitiser's `img src` check must compare the parsed origin and path prefix of `PUBLIC_MEDIA_BASE_URL`, not a raw string prefix (`https://media.example.evil`). | backend (slices 01, 17) |
