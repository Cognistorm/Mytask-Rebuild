## 2. What is correct (checked, no finding)
- **Purposes and the upload ticket.**
  - The three gig purposes are user purposes with fixed types: images JPG/JPEG/PNG ≤ S-078, documents PDF ≤ S-082 (`purposes.ts:65-76, 122-137`). Deny by default stays.
  - `gig_document` is refused with 403 `FEATURE_DISABLED` while S-080 is OFF, **before** any presigned POST exists (`files.service.ts:159-163`), and again on save (`gigs.service.ts:139-142`; update allows only the documents the gig already has, `:288-291`).
  - Restricted users cannot use their gig files (`files.service.ts:338`); gig create/update refuse them (QA probes).
- **Worker.**
  - Images are re-encoded to WebP variants (EXIF/GPS dropped, `limitInputPixels` 100 M, `failOn: 'error'`); the raw upload is deleted after processing (`file-scan.service.ts:177`). Image polyglots therefore never reach `public-media` as uploaded.
  - Documents: magic check, size re-check, virus scan, then a copy pinned to the scanned ETag **and** re-hashed against the scanned SHA-256 (SEC-63 / SEC-75 controls apply to the new purpose, `:122-153`).
  - The 24 h clean-up of ready-but-unattached public files now covers the three gig purposes and checks the three gig tables (`files-scan.sweeper.ts:170-191`); a gig save sets `attached_at` inside its transaction (`markAttached`, `gigs.service.ts:590-597`, the SEC-74 pattern).
- **Attaching files to a gig.** Every file must be the caller's own upload of the expected purpose, not deleted, not used by another gig, and `ready` (`checkFiles`, `gigs.service.ts:469-487`); lists are de-duplicated and capped by S-077 / S-081 (`gig-input.ts:198-209`). A file used by a gig cannot be deleted through `deleteFile` (409, `FileAttachments.register`, `:100-103`). Deleted gigs keep their files and still count as users, so a file can never move from a deleted gig to a new one.
- **Ownership.** Owner operations go through `ownGig` (`:446-450`): another user's or a deleted gig is 404. Analytics and the owner view are owner-only; staff operations are `@StaffRoute('gigs.moderate')` with an audit row in the same transaction (`admin-gigs.service.ts:383-392`).
- **HTML.** Descriptions are sanitised with the `user_text` allow-list on every write and the sanitised value is stored (`gig-input.ts:72-101`). The web page and the admin queue render only that stored value; the app renders it natively (no WebView). Rejection reasons and titles in emails are HTML-escaped (`templates.ts` `layout`, `esc`).
- **Reports.** The report limiter counts every attempt first (SEC-23 / I-31), the reason is 6–500 characters, one report per user and gig (unique key, race mapped to 409); EV-22 tells staff nothing about the reporter.
- **Analytics and personal data (ADR-012, Q-055).** No IP is stored or sent anywhere: the visitor is a daily-salted HMAC of the IP bucket and user agent, the salt lives two days in Redis; GeoIP is a local file; only the referrer's host is kept; raw `analytics_events` are dropped after 90 days (`analytics-partitions.sweeper.ts:1-7`). Owner views and bots are not counted.
- **Client side.** The web document link is `target="_blank" rel="noopener noreferrer"`; the app opens the server-built media URL in the browser. The new XHR progress path in `upload.ts:106-124` posts only to the presigned URL the API returned and resolves `false` on abort, error and timeout.

## 4. Info
- **I-57 Files of pending, rejected and staff-removed gigs stay public by URL.** Gig images and documents are public from the moment they are ready, before moderation, and a staff removal keeps them (needed for restore, AC-20). A seller can share the direct media link of content that staff rejected or removed. The plan limit bounds the volume (gigs × S-077 images + S-081 documents), and legacy behaved the same. Owner question for later: should a staff removal move the gig's files out of `public-media` until a restore? **Owner 2026-10-08 (Q-185): yes, for staff removal → ROADMAP 4.3.24.**
- **I-58 Document file names are public.** `gigDocument` returns `originalName` to everyone (`gigs.service.ts:573`). A seller's file name can carry personal data (e.g. a full name or "passport"). `cleanFileName` removes paths and control characters only. Legacy parity; consider a hint in the wizard (Owner text choice). **Owner 2026-10-08 (Q-186): yes → ROADMAP 4.3.25.**
- **I-59 The GeoIP file is downloaded without an integrity check.** `scripts/geoip-download.mjs` trusts HTTPS only. A broken file is handled safely (lookups return null). The Phase 6 weekly job should open the new file with `maxmind` and compare its build date before swapping.
- **I-60 Small-gig analytics can point at one visitor.** The owner sees the city breakdown per day; for a gig with one visit that day, the city of that one visitor is shown. Raw events also link `userId` with country and city for 90 days. Legacy showed the same; record it in the privacy notice (Phase 6 legal text).
- **I-61 Stored gig HTML is trusted at render time** (extends I-47). The web gig page (`service/[slug]/page.tsx:161`) and the admin queue (`apps/admin/src/app/gigs/page.tsx:93`) render the stored description with `dangerouslySetInnerHTML`. Today both write paths sanitise. The Phase 5 ETL must run `sanitizeRichText(…, 'user_text')` on every migrated gig description.
