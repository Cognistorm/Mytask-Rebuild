# Handoff — slice 01 part B-2c (social login, backend + admin keys) → QA + Security

Branch `feat/auth`. Date 2026-09-30. Builds on contract 1.2.0 (solution-architect handoff `2026-09-30-solution-architect-to-backend-engineer-social-settings-contract.md`) and the Owner answers to Q-155 and Q-156.

## What I did
- **`startSocialLogin` / `completeSocialLogin`** (ADR-002 §7), for Google, Facebook, GitHub, LinkedIn and X.
- **`state`:**
  - 256-bit random value, stored hashed in Redis for 10 minutes;
  - single use: read and deleted in one step (MULTI GET+DEL);
  - stored with the provider, client kind, redirect URI and `?ref=` code.
- **SEC-09 binding.** The check is chosen by the client kind stored with `state` (SEC-32(a)). Empty stored values never match.
  - **Web:** the `__Host-mt_oauth` cookie (HttpOnly, Secure, SameSite=Lax, 10 min) holds a nonce whose hash is stored with `state`. The API keeps the PKCE verifier. The cookie is cleared on every callback.
  - **Mobile:** `codeChallenge` (S256) is required. `codeVerifier` must hash to it and is sent to the provider.
- **Redirect-URI allow-list:**
  - web: `{APP_URL}/auth/{provider}/callback` and `{APP_URL}/en/auth/{provider}/callback`;
  - mobile: `{APP_URL}/app-return/auth/{provider}`.
- **Login rules:**
  - An existing link logs in through `issueSession()`, so status checks and 2FA apply (AC-30, AC-40). A deleted account → 401.
  - No link: only a verified email creates an account (Q-156). Google/LinkedIn need `email_verified`; GitHub needs a primary address marked verified. Facebook and X share no trusted email, so they get 422 `AUTH_SOCIAL_EMAIL_MISSING` unless a link exists.
  - An email already used by any account, including deleted ones → 409 `AUTH_SOCIAL_EMAIL_EXISTS` (AC-39).
- **New account** (AC-38):
  - active, email verified, no password;
  - username by the legacy rule (slug of nickname, else of name; `u` + 7 digits for names with no Latin letters), with an `_xxxx` suffix when taken;
  - referral code; a `?ref=` code is applied;
  - `ReferralService.creditSignup`; `isNewAccount: true`.
- **`social_accounts` table** (data-model §3.A) + migration `20260930200000_social_accounts`. `Me.socialProviders` now lists the linked providers.
- **Settings S-065…S-069** (ADR-005 §8): one structured value per provider.
  - The secret is sealed with AES-256-GCM (`SETTINGS_ENCRYPTION_KEY`, key id stored).
  - Reads return only `{ isSet, updatedAt }`. Leaving the secret out keeps it, a string replaces it, `null` clears it.
  - EC-10: switching ON without a client ID and secret → 422.
  - Audit and EV-124 show only `clientSecretSet` / `clientSecretReplaced`. Re-login required; critical row.
  - A secret sealed with a rotated-away key counts as "not set", so the provider is off.
- **Admin settings screen:** each provider row has an on/off switch, client ID, a new-secret field (empty = keep) and "clear secret". The saved secret is never shown.
- **Env:** `SETTINGS_ENCRYPTION_KEY` (base64 of 32 bytes) is required in production and generated by `pnpm setup:env`. It was appended to the Owner's local `.env`, which is git-ignored.
- **i18n:** 7 new keys (English + Georgian).
- **Tests:**
  - 9 API tests in `test/social.test.ts`, with the provider faked at the HTTP level;
  - 1 settings test in `test/staff.test.ts`; 73 API tests in total;
  - admin E2E `e2e/social-settings.spec.ts`; 5 admin E2E tests pass against `pnpm preview`.

- **QA:**

  - admin AC-54 and EC-10.
  - Parity: legacy logged in by email match only when the provider id matched (`legacy/APP/app/Livewire/Main/Auth/Social/Google/CallbackComponent.php`); we keep that, and add verified-email and SEC-09 rules.
- **Web + mobile entry points (not built):**
  - What's missing: login buttons, the web callback page `/auth/{provider}/callback`, and mobile `expo-auth-session`.
  - Why: clients learn the enabled providers from `getPublicConfig`. That schema covers the public settings of every slice (plans, payments, escrow, uploads…), and most of those rows don't exist yet, so a partial response would fail the contract.
  - Proposal: build `getPublicConfig` as a platform task early in slice 02, then add the buttons. Until then, social login is reachable only through the API. Every provider stays OFF until the Owner enters keys anyway.
- **Data migration:** move legacy `users.provider_name/provider_id` into `social_accounts`. These are the only way Facebook/X users can log in (Q-156).

## Open questions / risks
- **Linking from settings:** there is no "link a login provider from settings" operation, and legacy had none. New Facebook/X users cannot sign up. If the Owner wants linking, it is a new feature (spec + contract).
- **Avatars:** provider avatars are stored as a URL on `social_accounts`. Copying them into the user's avatar waits for the files foundation F0 (slice 02).
- **Provider endpoints:**
  - Endpoints are public provider documentation as of 2026 (Facebook Graph v19.0; X API v2). Real sign-in with each provider must be tried once keys exist.
  - LinkedIn and some Facebook app types may ignore PKCE parameters; the client secret is always sent server-side.
