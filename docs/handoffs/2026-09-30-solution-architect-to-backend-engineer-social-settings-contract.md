## What I did
1. **Q-155 (a) — contract 1.1.0 → 1.2.0 (additive).** Each social-login register row S-065…S-069 (`auth.social.google`, `.facebook`, `.github`, `.linkedin`, `.twitter`) is now one `structured` value instead of one bare secret string. Recorded as a revision of **ADR-005 §8** (no new ADR).
   New schemas (group D6, `docs/04-api/src/schemas/d6.yaml`):
   - `SettingSocialProviderValue` (read shape, in `SettingEntry.value` / `defaultValue` and `SettingVersion.value`): `{ isEnabled: boolean, clientId: string|null (≤512), clientSecret: SettingSecretStatus }`.
   - `SettingSecretStatus`: `{ isSet: boolean, updatedAt: Timestamp|null }`. The secret itself is never returned.
   - `SettingSocialProviderUpdate` (request shape of `SettingUpdateRequest.value`): required `isEnabled`, `clientId` (string 1…512 or null); optional write-only `clientSecret` (string 1…512 or null); `additionalProperties: false`. The secret field: **omitted** keeps the stored secret, **a string** replaces it, **`null`** clears it.
   Updated descriptions: `adminUpdateSetting`, `adminRestoreSettingVersion`, `SettingType`, `SettingValue`, `SettingEntry` (+ `isSet`), `SettingUpdateRequest`, `SettingVersion.value`.
   Rules not changed: EC-10 (after applying the change, `isEnabled: true` without `clientId` + stored secret → `422 BUSINESS_RULE_VIOLATION`, nothing saved); re-authentication (`stepUpFor` still lists S-065…S-069); critical rows / EV-124; secret rows cannot be restored (`422`).
2. **Q-156 (a, strict)** — recorded in **ADR-002 §7** as the adapter list of trusted-email providers, and made explicit in the `completeSocialLogin` description. Error codes did not change:
   - Trusted: `google`, `linkedin` (OIDC `email_verified = true`) and `github` (`/user/emails` entry with `verified: true`, primary verified address).
   - `facebook`, `twitter` (X): never create an account, never match or link one by email (even if the email equals an existing account's). They only log in to an account that already has a `social_accounts` row for that provider + provider user id. Otherwise → `422 AUTH_SOCIAL_EMAIL_MISSING`.
3. **Data model:** added `decision_reason text null` to `user_restrictions` (`data-model.md` §3.A, the line near 458), which is what `AdminRestriction.decisionReason` needs. Legacy has no such column, so migrated rows get null. The backend migration `20260930180000_restrictions` already has it. I also updated the `settings.value` note (§3.K) to the new stored shape.
4. Spec 00 rows S-065…S-069: the type column now says `structured` (the meaning is unchanged). I also updated the architecture.md summary lines and the ADR index row for 005, plus the contract README and the `info.description` change list.

## Open questions / risks
- **No "link a login provider from account settings" operation exists** (`putMyLinkedAccounts` is the S-123 profile-URL list, and legacy had none). So Facebook/X logins work only for accounts migrated with legacy `users.provider_name`/`provider_id`. New Facebook/X users cannot sign up with those providers. If the Owner wants linking from settings, that is a new feature (spec, contract, ADR). Nothing was invented here.
- Length limits (512 characters for client ID and secret) are technical input limits I chose. They are not business rules. Tell me if a provider needs longer values.
- GitHub: the contract says "the primary verified address is used". If the primary address is unverified, the login is treated as having no trusted email (422). Using a secondary verified address instead would need an Owner decision.
- The `SettingType` enum keeps `secret` for compatibility; no row uses it any more.
