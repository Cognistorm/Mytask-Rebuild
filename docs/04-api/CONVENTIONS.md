## 1. Workflow and files

### 1.1 Layout
```
docs/04-api/
  openapi.yaml                 GENERATED bundle (the contract clients generate from). Never edit.
  CONVENTIONS.md               this file
  README.md                    what lives where, commands, final coverage table
  realtime.md                  Socket.IO contract + event catalogue
  redocly.yaml                 lint config
  package.json, package-lock.json, scripts/   tooling (pinned Redocly CLI 2.55.0 + yaml)
  coverage/
    _TEMPLATE.md               row format
    NN.md                      one per spec, written by the spec's owning group
    16-dN.md                   spec 16 ACs delegated to group dN (§4.3)
  src/
    openapi.base.yaml          info, servers, tags, security schemes (foundation; architect only)
    openapi.root.yaml          GENERATED by scripts/build-root.mjs (base + $refs). Never edit.
    ownership.yaml             machine-readable ownership map (foundation; architect only)
    components/                shared schemas, parameters, responses, headers (foundation; read-only for groups)
    paths/f0-files.yaml        foundation paths (/files); also the reference example of every rule
    paths/dN-*.yaml            group N paths          ← group N edits
    schemas/dN.yaml            group N schemas        ← group N edits
    events/dN.yaml             group N realtime events ← group N edits
```

### 1.2 What a group run may edit
Only: its `src/paths/dN-*.yaml`, `src/schemas/dN.yaml`, `src/events/dN.yaml`, its `coverage/NN.md` files (+ `coverage/16-dN.md` if it has spec-16 delegations), and its handoff `docs/handoffs/2026-09-29-solution-architect-to-orchestrator-p2-b4-dN.md`.
Never: `src/components/*`, `src/openapi.base.yaml`, `src/ownership.yaml`, `openapi.yaml`, `src/openapi.root.yaml`, `realtime.md`, `README.md`, this file, other groups' files, specs, legacy. Need a change there? Put it under "Requests to the integration run" in your handoff (§18).

### 1.3 Verifying your work (parallel-safe)
```
cd docs/04-api
npm ci                        # once (installs the pinned tools)
npm run verify:group -- D3    # sandbox build of foundation + your files only; lint, bundle, checks
```
`verify:group` writes only to `docs/04-api/.build/dN/` (git-ignored). **Do not run** `npm run lint`, `bundle`, `verify` or `verify:final` during the parallel phase: they rebuild the shared generated files from everybody's half-written work. Those commands belong to the integration run.
A group run is finished only when `verify:group` prints `PASSED` with **0 errors** in every step (warnings about other groups' reserved operations not yet written are expected).

### 1.4 Style of the YAML
- `$ref` targets: shared `'../components/schemas.yaml#/Money'`, `'../components/parameters.yaml#/Cursor'`, `'../components/responses.yaml#/NotFound'`; own schemas from a path file `'../schemas/d3.yaml#/Withdrawal'`; own schemas inside the schema file `'#/Withdrawal'`; shared from a schema file `'../components/schemas.yaml#/Money'`.
- Never `$ref` another group's schema file (it may be half-written, and it couples groups). Use shared schemas (§2) or define what you need under your own prefix.
- OpenAPI 3.1 / JSON Schema 2020-12: nullable scalar `type: [string, 'null']`; nullable reference `oneOf: [{$ref: …}, {type: 'null'}]`; constants `const:`.
- Keep descriptions short and factual; cite the rule source in brackets (`spec 06 AC-11`, `ADR-003 §6`, `S-026`).

### 2.2 Parameters (`components/parameters.yaml`)
`AcceptLanguage` (header; **on every path item**), `IdempotencyKey` (header, required; money operations), `XMyTaskClient` (header; only where behaviour depends on the client, e.g. `createPayment`), `Cursor`, `Limit` (default 20, max 100), `AdminLimit` (default 50, max 200), `UserIdFilter` (`?userId=` on admin lists, §4.2), `CreatedFrom`, `CreatedTo`, `PageNumber` (`?page=N`, only on the public lists of §8.1).

### 2.3 Responses (`components/responses.yaml`) and headers (`components/headers.yaml`)
Responses: `BadRequest` 400, `Unauthorized` 401, `Forbidden` 403, `NotFound` 404, `Conflict` 409, `UnprocessableEntity` 422, `TooManyRequests` 429, `ServiceUnavailable` 503, `NoContent` 204, `FoundRedirect` 302. All error responses carry the `Error` body and `X-Request-Id`.
Headers: `XRequestId`, `RetryAfter`, `IdempotentReplayed`, `ContentLanguage`, `Location`, `ETag`.

### 2.4 Security schemes (`openapi.base.yaml`)
`userBearer` (JWT `aud=user`), `userCookie` (`__Host-mt_at`), `staffBearer` (JWT `aud=staff`), `staffCookie` (`__Host-mt_staff_at`). Refresh cookies: `__Secure-mt_rt` (path `/api/v1/auth`), `__Secure-mt_staff_rt` (path `/api/v1/admin/auth`). Copy-paste blocks: §6.2.

## 3. Naming

### 3.1 URLs and versioning
- Base path `/api/v1` is in `servers`; path keys start after it (`/gigs`, not `/api/v1/gigs`). Additive changes only within v1 (ADR-014 §5).
- Resource collections are **plural kebab-case nouns**: `/refund-requests`, `/custom-offers`, `/saved-cards`. Path parameters are camelCase and name the resource: `{gigId}`, `{escrowId}`, `{conversationId}`.
- Nesting at most two levels, and only for true sub-resources of a resource you own: `/gigs/{gigId}/reports`, `/escrows/{escrowId}/deliveries`. Never nest under another group's prefix (§4.1).
- Singletons of the caller: `/me`, `/cart`, `/wallet` (no id).
- **State-changing actions** that are not plain CRUD are `POST /{collection}/{id}/{verb}` with a kebab-case verb: `/custom-offers/{customOfferId}/decline`, `/orders/{orderId}/items/{orderItemId}/start`, `/admin/withdrawals/{withdrawalId}/mark-paid`. When the action creates a record, model the record instead: `POST /escrows/{escrowId}/revision-requests`.
- The canonical path parameter is the uuid `id`. Public legacy identifiers (gig `uid`, project `pid`, order/offer/refund `uid`, withdrawal `number`) are exposed as fields and looked up with `GET /{collection}/lookup?uid=…` (or `?pid=`, `?number=`), returning the same schema as the canonical GET. Exception: users are addressed by `{username}` on public profile paths (`/users/{username}`, reserved `getUserProfile`).
- No trailing slash, no file extensions, no verbs in collection names, no query-string actions.

### 3.2 Methods and status codes
| Method | Use | Success |
|---|---|---|
| GET | read; never changes state | 200 (302 only for downloads) |
| POST | create (201 + created resource) or action (200 + updated resource, 202 if asynchronous) | 201 / 200 / 202 |
| PATCH | partial update; omitted fields unchanged, `null` clears a nullable field | 200 + resource |
| PUT | full replace of a singleton or idempotent upsert (`/cart/items/{gigId}`, `/push-tokens/{installationId}`) | 200 |
| DELETE | delete / remove | 204 |
Single resources are returned **bare** (no `{data: …}` wrapper); lists are `…Page` objects (§8).

### 3.3 operationId
- camelCase `verb + Resource(+Qualifier)`, unique in the whole contract: `listGigs`, `getGig`, `createGig`, `updateGig`, `deleteGig`, `lookupGig`, `submitGigForReview`, `startOrderItem`, `declineCustomOffer`, `markWithdrawalPaid`.
- Standard verbs: `list`, `get`, `lookup`, `create`, `update`, `replace`, `delete`, `put` (singleton upsert); domain verbs for actions (`approve`, `reject`, `publish`, `hide`, `unhide`, `remove`, `restore`, `start`, `cancel`, `complete`, `accept`, `decline`, `withdraw`, `award`, `revoke`, `resolve`, `release`, `refund`, `markPaid`, `resend`, `verify`, `export`…).
- **Admin operations start with `admin`**: `adminListGigs`, `adminApproveGig`, `adminMarkWithdrawalPaid`. Only `/admin/*` operations may start with `admin` (checked).
- The reserved operationIds (§5.1) must be used exactly.

### 3.4 Schemas, properties, enums
- Schema names PascalCase and start with one of **your group's schema prefixes** (`ownership.yaml → schemaPrefixes`), optionally preceded by `Admin` (`AdminWithdrawal`). Exception: `DnErrorCode`. Checked by the build.
- Suffixes: `…Request` for request bodies, noun first so the prefix rule holds (`GigCreateRequest`, `GigUpdateRequest`, `WithdrawalCreateRequest`); `…Page` for lists; `…Event` for realtime payloads; `Admin…` for staff views that show more than users see (`AdminWithdrawal`, `AdminWithdrawalPage`).
- Properties camelCase. Booleans read as facts: `isPremium`, `hasDelivery`, `canReview`. Counts end in `Count`. Timestamps end in `At` and are `Timestamp`. Money properties are `Money` (never `…Tetri`, never `number`). Percentages are `BasisPoints` and end in `Rate` or `Bp`.
- Enum values `snake_case`, matching `data-model.md` §4 status names exactly (`awaiting_payment`, `revision_requested`, `accepted_by_seller`…). Add a `description` for non-obvious values. Clients treat unknown values as "other" (ADR-014 §5).
- Responses: every property listed in `required`; unknown or not applicable = `null` (never absent). Requests: `required` only for truly required fields; set `maxLength`/`minLength`/`minimum`/`maximum` from the spec's limits (they are the API's validation).
- Identifiers: every resource exposes `id` (uuid) plus its public identifier if it has one (`uid`, `pid`, `number`).

### 4.2 Admin endpoints: one rule
**The group that owns a resource also owns its `/admin/<resource>` endpoints**, and implements the staff ACs of its own specs **and** the spec 16 ACs about that resource (list in §4.3). D6 owns only the admin *platform* (staff auth, staff/roles, audit, dashboard, reports queue, settings and fee rules, custom code, translations, analytics, system/logs/health/maintenance/caches, notification delivery log).
Consequences:
- Every admin list that shows items involving a user supports the shared `UserIdFilter` (`?userId=`) so the user page tabs of spec 16 AC-31 are just calls to the owners' lists.
- Admin moderation queues follow spec 16 AC-19 (oldest first, 50 per page → `AdminLimit`, filters date/owner/category, decisions with `StaffReasonRequest`, first decision wins → `409 STATE_CONFLICT` with `messageKey: t_item_already_decided`, audit).
- Staff downloads of private files are the owner's admin operation: `GET /admin/<resource>/{id}/files/{fileId}/download` (302 or `?mode=json`, same as `getFileDownload`), permission of that resource, audited (`x-audit`). Example: D1 `GET /admin/kyc/{kycId}/files/{fileId}/download` with `kyc.review`.
- Staff actions on users that move money or points belong to D3 (`/admin/ledger/adjustments`, `/admin/points/adjustments`, `/admin/subscriptions/…` gift/cancel), the rest of user actions to D1.

### 5.2 Escrow operations are shared by gigs, projects and offers (D4)
Data-model §3.I: one escrow per paid item, one delivery/revision/auto-release/refund implementation. So:
- D4 writes `/escrows/{escrowId}` (read), `/escrows/{escrowId}/deliveries` (list, create: message + optional one `delivery` file), `/escrows/{escrowId}/revision-requests`, `/escrows/{escrowId}/complete` (buyer completes → release), and refunds/disputes/unblock keyed by `escrowId`. Policies inside check the item type (buyer = client of the contract, etc.).
- D5 contracts and D4 order items / custom offers embed `escrow: EscrowSummary | null` (null before payment) and `conversation: ConversationRef`; they do **not** define their own deliver/revise/complete operations.
- Item-specific actions stay with the item: `start` (gig order item), `cancel` before start (order item), offer `cancel` by the freelancer (spec 12), contract hire-cancel before payment (spec 11).
- D5 coverage rows for spec 11 delivery/revision/completion ACs name the reserved D4 operations (`API` rows); D4 adds those ACs to the operations' `x-covers` (it is told here which: spec 11 "Work, delivery and revisions", "Completion", "Automatic release"; spec 12 "Work, delivery, revisions", "Completion and auto-release").

### 5.3 Threads are conversations (D5)
Order-item, project, custom-offer and refund threads are conversations (`ConversationKind`). The item embeds `ConversationRef`; messages are read and written only through D5's reserved operations. Staff writing "as MyTask" in refund threads uses `adminCreateConversationMessage` (permission `refunds.thread.write` for refund threads; D5 documents that `chat.read` is needed to read other kinds). Delivery and revision records are D4 escrow records; D5 may show them in the thread as system messages (`kind: system_event`).

### 5.4 Payments: one checkout for every purpose (D3)
- `POST /checkout/quote` (`createCheckoutQuote`) takes a `CheckoutTarget` and returns the server-computed breakdown per available method (items, buyer fees as `FeeLine`s, card surcharge only for `bog_card`, promo discount only for promo-eligible services, total) and an opaque `quoteId` (the quote hash, data-model `payments.quote_hash`).
- `POST /payments` (`createPayment`, `x-money`, `Idempotency-Key`) takes `{ target: CheckoutTarget, method: PaymentMethod, quoteId, saveCard?, promoCode? }`. If the recomputed quote differs → `409 QUOTE_CHANGED` with the new quote in `details` (spec 05 AC-8). Result: the payment plus what to do next (redirect URL to BOG / completed / bank-transfer instructions). It creates the gig order from the cart (spec 06 AC-7…AC-9) or funds the contract payment / offer / top-up / subscription.
- D4 (cart, offers) and D5 (contracts) do **not** write pay endpoints; their coverage rows for "pay" ACs name `createCheckoutQuote` / `createPayment` (reserved) and their items expose `payment: PaymentSummary | null` where the spec shows payment state. D3 documents the effects per purpose in `createPayment`'s description and covers those ACs in `x-covers` (spec 06 AC-7…AC-12, spec 11 payment ACs, spec 12 pay ACs).
- Return pages poll `getPayment`; they never change state (ADR-004 §3, url-map §7).
- Mobile Premium by card: `createPayment` reads `X-MyTask-Client`; `ios`/`android` with purpose `subscription` while S-126 is OFF → `403 FEATURE_DISABLED` (ADR-016 §3).

### 5.5 Reports
Creation stays with the reported resource (rules differ per type): D1 `POST /users/{username}/reports`, D2 `POST /gigs/{gigId}/reports`, D5 `POST /projects/{projectId}/reports` and `POST /proposals/{proposalId}/reports`. The one staff queue is D6 `/admin/reports` (`reports.handle`, P-118). Queue shortcuts (remove gig, hide project, reject proposal, restrict/ban) call the owners' admin operations.

### 5.6 Reviews
D2 owns `/reviews`. A review targets a `WorkItemRef` (order item, contract payment, custom offer). Items embed `reviews: ReviewRef[]` (or `myReview`/`theirReview`) where the spec shows them; D2 exposes `canReview` logic in its own operations.

### 5.7 Users, public config, settings
- Show users only as `UserSummary` outside D1.
- Public settings for clients come from D1's `getPublicConfig` (ADR-005 §9). A group that needs a new public setting names the register row in its handoff; D1 includes every row flagged "public" in spec 00 §4 (D1 decides the shape `PublicConfig`).
- Settings are written only through D6 (`adminUpdateSetting`); fee rules through D6 `/admin/fee-rules` (the Commission & Fee UI). Domain groups never expose settings writes.

### 5.8 Requests to the integration run
If you need a new shared schema, a change to a shared one, a new prefix, a new reserved operation, or a new `FilePurpose`: define a local stand-in under your prefix if you can, and list it under "Requests to the integration run" in your handoff. The integration run decides and edits the foundation files.

## 6. Security and `x-permission`

### 6.1 `x-permission` (required on every operation)
```yaml
x-permission:
  audience: user          # public | optional-user | user | restricted-user | staff | webhook
  ownership: buyer or freelancer of the escrow; others get 404   # required unless audience is public/webhook ("none" if not resource-bound)
  permission: withdrawals.approve   # staff only: exactly one name from spec 16's catalogue (ownership.yaml staffPermissions) or '@self'
  permissionBy:           # staff only, optional: the ONE permission checked is selected by one attribute (below)
    attribute: purpose (request body)
    map: {category_image: catalog.write, blog_image: content.write}
  stepUp: true            # staff only: spec 16 AC-7 re-authentication within 15 minutes (else 403 REAUTH_REQUIRED)
  stepUpFor: [S-100, S-110]  # staff only, instead of stepUp: re-authentication only for these register rows (settings writes)
  plan: premium           # only if Premium is required (e.g. proposals, Q-020) → 403 PREMIUM_REQUIRED
  toggles: [S-034]        # register switches that must be ON → 403 FEATURE_DISABLED (00 AC-11)
  notes: free text for anything else (e.g. "not while a dispute is open")
```
| audience | Meaning | `security` |
|---|---|---|
| `public` | anyone, no token needed (or ignored) | `security: []` |
| `optional-user` | works for guests; a signed-in user gets more (e.g. own gig page, favourites flag) | `security: [{}, {userBearer: []}, {userCookie: []}]` |
| `user` | active signed-in user; **restricted users are refused** (`403 ACCOUNT_RESTRICTED`, ADR-002 §4) | omit (root default) |
| `restricted-user` | signed-in user **including** restricted ones (restriction notice, appeals, `/me`, logout, own notifications) | omit (root default) |
| `staff` | staff token on the admin host; one permission (or `@self` for own session/profile) | `security: [{staffBearer: []}, {staffCookie: []}]` |
| `webhook` | provider callback, no user auth; verified in the handler (§10) | `security: []` |
- `ownership` is written in words from the spec (who is allowed relative to the resource): "self", "owner of the gig", "buyer of the order", "freelancer of the escrow", "participant of the conversation", "project owner (client)", "author of the proposal", "none".
- **404 vs 403**: if a non-party must not learn that a private resource exists (orders, offers, conversations, files, hidden/pending items of others), answer `404`. Use `403` when the resource is visible but the action is not allowed (owner reporting own gig, plan/toggle/restriction refusals).
- `@self`: staff acting only on their own session/profile (`adminGetMe`, own profile edit, `adminReauthenticate`, `adminLogout`, own file status). Spec 16 AC-9 requires one permission per admin operation; `@self` is the documented exception for these (§6.3, Owner question D6-Q1).
- Staff mutations that change nothing (pure computations such as `adminPreviewFeeRule`) carry `x-audit-exempt: <reason>` instead of `x-audit`; `check-contract` refuses a staff POST/PUT/PATCH/DELETE with neither.
- **One permission per call (spec 16 AC-9) — the one rule.** Every staff operation checks exactly one catalogue permission. Usually it is fixed (`permission`). Where the resource decides which screen's permission applies, `permissionBy: {attribute, map}` selects that one permission from **one** attribute of the request or resource. The map lists **every** allowed value explicitly; a value that is not in `map` is **denied** (`403 FORBIDDEN`), never mapped to a fallback (P2-B5 item 13). `permission` must be one of the map values (it is the value shown by tools that read only one name). There are no "either/or" permissions. Uses: `adminCreateFileUpload` (by upload purpose; purposes outside the map are also refused with `422 FILE_PURPOSE_MISMATCH`), `adminUpdateSetting` / `adminRestoreSettingVersion` (by the register row's settings area), `adminGetConversation` / `adminListConversationMessages` (by conversation kind: refund threads need `refunds.thread.write`, the other four kinds `chat.read` — Owner question Q-D5-4). `check-contract` validates every map value against the catalogue and that `permission` is a map value.
- `stepUpFor: [S-nnn…]` is row-conditional step-up for the generic settings write (spec 16 AC-7 names S-065…S-069, S-100, S-110, S-127); it replaces `stepUp` there and also requires 403.
- Every staff mutation writes the audit log; declare it with `x-audit: <action>` (e.g. `withdrawal.mark_paid`). Sensitive staff reads (conversation open, KYC file, exports, secret status) also carry `x-audit`.
- CSRF (ADR-002 §2, SEC-14; global, do not add per operation): **every** POST/PUT/PATCH/DELETE that is not authenticated with `Authorization: Bearer` — including the public auth operations that read or set cookies (`register`, `login`, 2FA verify/resend, `refreshSession`, `logout`, social start/callback, password and email links, and the `/admin/auth/*` ones) — needs `X-MyTask-Client` and, when it carries a cookie, is a `web`/`admin` client or has an `Origin` header, an `Origin` **exactly equal** to the origin of the host it was sent to (`https://mytask.ge` or `https://admin.mytask.ge`; never a same-site or suffix match, because `admin.` and `staging.` are same-site). Else `403 CSRF_CHECK_FAILED`. Bodies are `application/json` (else `400 VALIDATION_FAILED`, field code `unsupported_content_type`); the only exception is the RFC 8058 one-click form POST of `unsubscribeNotificationEmail`. Webhooks never read cookies.
- Login/refresh/2FA operations are `public` (they issue tokens). Staff login is `public` on `/admin/auth/*` (the only non-staff audience allowed under `/admin`).

### 6.2 Copy-paste security blocks
```yaml
# user / restricted-user: no `security` key (root default: userBearer or userCookie)
security: []                                              # public, webhook
security: [{}, {userBearer: []}, {userCookie: []}]        # optional-user
security: [{staffBearer: []}, {staffCookie: []}]          # staff
```

### 6.3 The `@self` exception (for the Owner, spec 16 AC-9)
Spec 16 AC-9: "every admin API operation requires exactly one permission from the catalogue". The contract keeps that meaning for **every operation that touches data other than the caller's own staff account**. The only operations without a catalogue permission are those where a signed-in staff member acts on **their own** session or profile, which the catalogue has no entry for: `adminLogout`, `adminReauthenticate`, `adminRequestReauthCode`, `adminGetMe`, `adminUpdateMe`, `adminChangeMyPassword`, `adminRequestMyEmailChange`, `adminCreateMaintenancePreviewLink` (spec 16 AC-70: any signed-in staff member may preview), and F0's `adminGetFile` / `adminCompleteFileUpload` (own uploads only). They are declared `permission: '@self'`, are still deny-by-default in code (an explicit `@self` guard, so the startup check of AC-9 passes), are audited when they change something, and can never reach another person's data. Pre-login operations (`adminLogin`, 2FA verify/resend, refresh, password reset/set, email confirm) are `public` by nature. The alternative — a new always-granted catalogue permission such as `self.manage` — would change the approved catalogue (P-114); the Owner decides at the gate (D6-Q1).

## 7. Errors

### 7.1 Body
Always the shared `Error` `{ code, message, details }`. `message` is localized (`Accept-Language`) from the spec's `t_*` key; put that key in `details.messageKey`. Validation errors list fields in `details.fields[]` (`FieldError {field, code, message, messageKey}`); use the spec's `t_*` keys as `messageKey` where the spec names them. Other well-known `details` members: `permission`, `settingId`, `limit`, `retryAfterSeconds`, `currentState`. Operation-specific extra members are allowed; document them in the response description (e.g. `QUOTE_CHANGED` → `details.quote`).

### 7.2 HTTP status mapping and minimum responses
| Status | When | Codes |
|---|---|---|
| 400 | malformed or invalid input (schema, lengths, patterns, allowed characters) | `VALIDATION_FAILED`, `IDEMPOTENCY_KEY_REQUIRED` |
| 401 | not authenticated | `UNAUTHENTICATED` (+ D1 auth codes on login) |
| 403 | authenticated but not allowed | `FORBIDDEN`, `CSRF_CHECK_FAILED`, `ACCOUNT_RESTRICTED`, `REAUTH_REQUIRED`, `FEATURE_DISABLED`, `PREMIUM_REQUIRED`, domain codes |
| 404 | missing or must stay hidden | `NOT_FOUND` |
| 409 | state conflict / duplicate / concurrent | `STATE_CONFLICT`, `DUPLICATE`, `IDEMPOTENCY_IN_PROGRESS`, domain codes (`QUOTE_CHANGED`) |
| 422 | valid request refused by a business rule | `BUSINESS_RULE_VIOLATION`, `PLAN_LIMIT_REACHED`, `INSUFFICIENT_FUNDS`, `IDEMPOTENCY_KEY_REUSED`, `FILE_*`, domain codes |
| 429 | throttled | `RATE_LIMITED`, domain throttle codes |
| 503 | maintenance / dependency down | `MAINTENANCE`, `SERVICE_UNAVAILABLE` (global; do not list per operation) |
Minimum per operation (checked where marked ✓): at least one 4xx ✓; `401` on every authenticated operation ✓; `400` when there is a body or query input; `403` when there is `ownership`, `permission`, `plan`, `toggles` or `stepUp` (✓ for stepUp); `404` when there is a path id; `409`+`422` on `x-money` ✓; `429` when `x-rate-limit` is set. Use only the shared response objects ✓ (so every 4xx/5xx is `Error`).
List in each response's `description`, when useful, which codes that operation can return (e.g. `'409': STATE_CONFLICT (already started), ORDER_ALREADY_DELIVERED`). Since responses are `$ref`s, put the list in the operation `description` under a line "Errors:".

### 7.3 Error code catalogue
- `CommonErrorCode` (shared, fixed now) covers everything cross-cutting (see the schema's `x-enumDescriptions`).
- Each group defines `DnErrorCode` in its schema file: `type: string`, `enum`, and `x-enumDescriptions` with `"[status] meaning; messageKey t_…"` per code. Remove `x-stub: true`.
- Codes are `UPPER_SNAKE_CASE` and must start with one of the group's **error prefixes** (checked):
  D1 `AUTH_ ACCOUNT_ USER_ PROFILE_ PORTFOLIO_ KYC_ RESTRICTION_ APPEAL_ IP_BAN_ EMAIL_ PASSWORD_ TWO_FACTOR_ SESSION_` ·
  D2 `CATEGORY_ SKILL_ COUNTRY_ SEARCH_ GIG_ FAVORITE_ REVIEW_ PAGE_ BLOG_ COMMENT_ CONTACT_ NEWSLETTER_ SEO_ SITEMAP_ REDIRECT_ OUTBOUND_ HOME_` ·
  D3 `CHECKOUT_ QUOTE_ PAYMENT_ WALLET_ TOPUP_ BANK_TRANSFER_ CARD_ BILLING_ LEDGER_ ADJUSTMENT_ SUBSCRIPTION_ POINTS_ REFERRAL_ PROMO_ WITHDRAWAL_ PAYOUT_` ·
  D4 `CART_ ORDER_ OFFER_ ESCROW_ DELIVERY_ REVISION_ COMPLETION_ REFUND_ DISPUTE_ UNBLOCK_` ·
  D5 `CHAT_ CONVERSATION_ MESSAGE_ PROJECT_ PROPOSAL_ AWARD_ CONTRACT_ HIRE_` ·
  D6 `NOTIFICATION_ PUSH_ PREFERENCE_ ANALYTICS_ STAFF_ ROLE_ PERMISSION_ AUDIT_ SETTING_ FEE_ TRANSLATION_ CUSTOM_CODE_ REPORT_ SYSTEM_ EXPORT_ WEBHOOK_SENDGRID_`.
- Prefer a common code + `details.messageKey` over a new domain code; add a domain code only when a client must **branch** on it (e.g. `QUOTE_CHANGED`, `AUTH_TWO_FACTOR_REQUIRED`, `ORDER_ITEMS_NO_LONGER_AVAILABLE`).
- Clients show `message`; they never hard-code texts per code (texts belong to i18n keys).

## 8. Pagination, filters, sorting
- Every list is cursor-paginated: parameters `Cursor` + `Limit` (users) or `AdminLimit` (admin). Response `…Page`:
```yaml
GigCardPage:
  allOf:
    - $ref: '../components/schemas.yaml#/CursorPage'
    - type: object
      properties:
        data:
          type: array
          items: {$ref: '#/GigCard'}
```
- Never return a bare array (checked). Small fixed reference lists (categories tree, countries, plans) are returned as an object with a named array (`{ categories: [...] }`), not paginated.
- `totalCount` only when the spec needs a number (queue counters, "N results"); say so in the description.
- Page sizes from the spec go in the description (e.g. "40 per page, spec 05 AC-31"); the server uses that default.
- Filters are camelCase query parameters named after the property (`status`, `categoryId`, `sellerUsername`, `role`); multi-value filters repeat the parameter (`?status=paid&status=in_progress`, `style: form, explode: true`); date ranges use `CreatedFrom`/`CreatedTo` (or `<field>From`/`<field>To`); free text is `q`.
- Sorting: one `sort` enum parameter with snake_case values from the spec (`recommended`, `newest`, `price_asc`, `price_desc`, `rating`, `oldest`); the default is stated.
- Cursor lists are stable under inserts (keyset pagination, ADR-011, data-model indexes).

### 8.1 Numbered web pages (ratified by the integration run)
The website keeps numbered page URLs (`?page=N`, url-map §2, ADR-011 §4) on six public lists: `searchGigs`, `searchProjects`, `listSellers`, `listHireSellers`, `listReviews`, `listBlogArticles`. These operations accept the shared `PageNumber` parameter (`page`, 1-based, ≤ 1000) **as an alternative to** `cursor` (both → `400 VALIDATION_FAILED`) and return `totalCount`. The response is the same `…Page` (`nextCursor` is still filled, so a client can continue with cursors). No other list gets `page`; mobile uses cursors only. `check-contract` refuses `page` on anything that is not a cursor list.

## 9. Money and idempotency

### 9.1 Money
- All amounts are the shared `Money` (`amount` integer tetri, `currency: "GEL"`), in requests and responses. No `number` types anywhere (checked), no `…Tetri` properties (checked), no strings with decimals.
- Percentages are `BasisPoints` (250 = 2.5%). Rounding is the API's job (half up to the tetri, R-3.8); clients never compute totals, fees or surcharges — they show `createCheckoutQuote` results (spec 05 AC-5).
- Amounts may be negative only where the spec says so (migrated negative balances, ledger/transaction lines with a sign); say so in the property description.
- Points are **not** money: plain integers (`points`, `pointsBalance`), separate ledger (ADR-003 §9).
- Fees appear as `FeeLine` with `feeRuleVersionId` (snapshot, 00 AC-9).

### 9.2 `x-money: true` — which operations
Every operation that **can post a money or points journal** (directly, or through the state change it makes) — for example: `createPayment` (incl. top-up and subscription), wallet payment, `completeEscrow`, order-item cancel before start, freelancer offer cancel, refund accept (freelancer), dispute decision, `adminReleaseEscrow`, `adminRefundEscrow`, unblock approve, withdrawal create / mark paid / reject, ledger adjustment, legacy-hold release/write-off, points add/deduct, Premium with points, bank-transfer confirm/reject, referral reward claim if any.
Such operations must: reference `IdempotencyKey` (required header) ✓, document `409` and `422` ✓, return the resulting resource (so a replay returns the same body with `Idempotent-Replayed: true`).

### 9.3 Idempotency semantics (ADR-003 §6)
Same key + same body within 24 h → stored response replayed; same key + different body → `422 IDEMPOTENCY_KEY_REUSED`; same key while the first is running → `409 IDEMPOTENCY_IN_PROGRESS` + `Retry-After`. Keys are per caller. Server-side, every journal also has a unique `idempotency_ref`, so webhook replays and job retries post once. Chat messages use the body field `clientMessageId` (UUID) instead of the header (ADR-007 §2); state transitions are compare-and-set (`409 STATE_CONFLICT` when the state changed).

## 10. BOG webhook pattern (D3; ADR-004 §3–§5)
```yaml
/webhooks/bog:
  parameters: [AcceptLanguage]
  post:
    operationId: handleBogWebhook
    tags: [Webhooks]
    security: []
    x-permission: {audience: webhook, notes: 'verified by provider callback + server-side status check'}
```
Rules the D3 run must write into the operation:
1. Raw body kept (content `application/json` with a permissive schema; the adapter maps field names; do not model BOG's schema beyond the fields we read: order id, status).
2. Optional header parameter `Callback-Signature` (the `verifyCallback` hook; checked only if the lead developer confirms signed callbacks — Q-087 table in ADR-004).
3. The handler stores the raw event (`payment_events`), answers **200 quickly with an empty body**, and processes asynchronously; unknown order ids are logged and still answered 200 (no retry storm); malformed bodies 400.
4. Processing **always** calls BOG's payment details (`getPaymentDetails`) and applies the payment only if BOG reports it paid for the same order, amount and currency; then one DB transaction: payment CAS `pending → paid`, journal `bog:{bogOrderId}:paid` (unique), business effect; otherwise `paid_unapplied` to the wallet (spec 05 AC-15). Replays are no-ops (AC-14).
5. A worker reconciles pending card payments after 5 minutes (ADR-004 §4) — covered as `API+JOB`/`NOT-API:job` rows with `getPayment` exposing the state.
6. Return URLs (`/payments/{id}/result`, `mytask://payments/{id}/result`) only poll `getPayment` (spec 05 AC-11).
7. Maintenance mode does not block it (spec 16 AC-70). Rate limit (ADR-004 §3, SEC-10): BOG's confirmed callback ranges are exempt; other sources 60 requests/min per IP (600/min per IP for everyone while BOG's ranges are unconfirmed) → `429`.
8. **Flood hardening (ADR-004 §3, SEC-10).** Body cap 64 KB (refused before parsing, not stored). Our payment is looked up by the BOG order id **before** any BOG call: unknown ids never call BOG and are never queued (capped log, at most 100 stored `unknown_order` events per hour, then a counter and one alert per hour); payments that are no longer `created`/`pending` are stored for staff and not queued; pending payments queue one job with id `bog-verify:{paymentId}` (dedupe shared with the reconciliation and "Check status").

## 11. i18n
- Every path item declares `AcceptLanguage` ✓. Responses may set `Content-Language`.
- **Reads** of translatable content return one resolved string per field in the requested language plus `contentLocale: ka|en` on the resource (Georgian fallback when English is missing, Q-023; never 404 because a translation is missing).
- **Writes** of translatable content (owner forms, staff editors) use `LocalizedString {ka, en}` per field; `ka` required (Latin allowed, Q-022), `en` optional and rejecting Georgian letters (R-5.4) → `VALIDATION_FAILED` with field `title.en`, code `georgian_letters_not_allowed`. Owner/staff "edit" reads return `LocalizedString` too (so the form shows both languages).
- UI strings are not in the API except `getI18nBundle` (base + admin overrides, ADR-006 §4). Never return pre-rendered sentences for UI chrome; return data + `t_*` keys (e.g. notifications carry `textKey` + `params`).
- The user's `locale` (stored on the account, D1) decides emails and push; `Accept-Language` decides only the HTTP response.
- Slugs are generated by the API (ADR-006 §8); clients never send slugs for gigs/projects.

## 12. Coverage and `x-covers`

### 12.1 On operations
`x-covers: ['06 AC-7', '05 AC-9']` — two-digit spec number, space, `AC-n` (checked against the specs). List every AC the operation implements (fully or its API part). An operation that implements no AC by itself (helpers, infrastructure) has `x-covers: []` **and** `x-covers-note: <why>` ✓. If you implement another group's AC because of §5.2/§5.4, add it too (e.g. D4's `createEscrowDelivery` lists `11 AC-32`).

### 12.2 Coverage files
One file per spec, `docs/04-api/coverage/NN.md` (owner group), plus `coverage/16-dn.md` for spec-16 delegations. Format: `coverage/_TEMPLATE.md`. Every AC of the spec appears **exactly once**, in AC order:
`| AC-n | summary ≤ 12 words | coverage | operation ids in backticks / reason |`

| Coverage | Meaning | Required content |
|---|---|---|
| `API` | one or more operations implement it | backticked operationIds (own, reserved or shared); each own operation lists the AC in `x-covers` ✓ |
| `API+JOB` | operations plus a background job (ADR-008) | operationIds exposing/triggering it + `job <name>` |
| `NOT-API:ui` | client-only (layout, wording, navigation, client state) | reason + the operation that supplies the data, if any |
| `NOT-API:job` | worker only, no endpoint (sweeper, reconciliation, renewal) | job name + ADR-008 section + operation exposing the result |
| `NOT-API:email` | email/push content or template | spec 15 event id + the operation/job that triggers it |
| `NOT-API:infra` | proxy, headers, robots, CSP, hosting, storage config | where it is configured (ADR/url-map) |
| `NOT-API:migration` | ETL / data migration only | data-model §12 reference |
| `NOT-API:policy` | a cross-cutting rule enforced inside many operations | how it is enforced (e.g. `x-permission.toggles`) + example operations |
| `NOT-API:content` | editorial content (legal text, blog posts) | who writes it |
| `DELEGATED:Dn` | another group implements it and writes the real row | reserved operationId if known, else the owner's prefix |
`DELEGATED` is allowed only where §4.3 (spec 16) or §5 says so, or for spec 00/01 ACs implemented by another group (e.g. spec 01 staff ACs → D6). The integration run resolves every `DELEGATED` row; `check-coverage --final` fails while any AC has only `DELEGATED` rows.
Header of the file: group, spec, totals (see template). Notes for the integration run at the bottom.

### 12.3 The merged table
The integration run runs `npm run verify:final`, which writes `coverage/SUMMARY.md`, and copies it into `docs/04-api/README.md` (§ Coverage). Gate item 7: every approved AC covered.

## 14. Rate limits and client IP
- **Client IP (normative, ADR-013 §14–§19, SEC-01).** Every "per IP" key below and in any `x-rate-limit`, every IP ban check, session/device/audit IP and analytics hash uses the one client IP resolved by the API's `ClientIpResolver`: the canonical header `X-MyTask-Client-IP` set by Caddy, trusted **only** when the TCP peer is Caddy (`TRUSTED_PROXY_IPS`); Caddy itself trusts `CF-Connecting-IP` only from Cloudflare's ranges and strips every client-sent forwarding header; the origin accepts traffic only from Cloudflare (or Caddy uses the TCP peer when there is no Cloudflare). The Next.js servers may pass a visitor IP/UA (`X-MyTask-Visitor-IP` / `-UA`) only with `X-MyTask-Service-Auth` = `INTERNAL_SERVICE_TOKEN` on the internal network, never through Caddy. `X-Forwarded-For`, `X-Real-IP`, `CF-*` are never read by the API. There are no "trusted proxy headers" other than these.
- Declare throttled operations with `x-rate-limit: '<limit> per <key>'` and a `429` response. Use the spec's numbers and register rows: login throttling S-062/S-063 (per account + IP), staff IP ban S-064, 2FA resend (60 s cooldown, 5 per 15 min, spec 01 R-A6), email-sending endpoints (spec 01 R-A9 fixed limits), contact form / newsletter / reports (spec 17 / 02 / 04), chat send (spec 08), uploads (60 / 10 min per user, foundation).
- **Per-account auth throttles (ADR-002 §5–§6, P2-B5).** (a) `login`: besides S-062 per account + IP, a per-account counter across all IPs → slow mode (20 failures/hour → 1 attempt per 30 s, `429 AUTH_LOGIN_THROTTLED`, no hard lock; SEC-02). (b) 2FA code checks (`verifyTwoFactorLogin`, `adminVerifyTwoFactor`, code re-authentication): 10 wrong codes per account per hour across all challenges → `429 TWO_FACTOR_LOCKED` / `STAFF_TWO_FACTOR_LOCKED` for S-063 minutes (SEC-03). (c) In-session password or code checks (`updateMe`, `changeMyPassword`, `updateMyTwoFactor`, `revokeMyOtherSessions`, `putPayoutDetails`, `adminReauthenticate`, `adminChangeMyPassword`): S-062 wrong answers per account in 15 minutes → further checks refused for S-063 minutes, `429 RATE_LIMITED` with `messageKey t_too_many_login_attempts` (SEC-04). The numbers 20/30 s/10 are technical constants until spec 01 makes them register rows.
- **Per-user anti-abuse limits (SEC-23; technical defaults, constants in code):** new conversations (`createConversation` answering `201`) 20 per hour per user; `createCustomOfferRequest` 20 per hour per user; the four report operations (`createGigReport`, `createUserReport`, `createProjectReport`, `createProposalReport`) together 10 per hour per user. Over the limit → `429 RATE_LIMITED` with `Retry-After`.
- Global defaults (not declared per operation): 600 requests/min per user or IP for reads, 120/min for writes; staff 1,200/min. Exceeding them gives `429 RATE_LIMITED` with `Retry-After`.
- Health is not rate-limited. Webhooks are not rate-limited per user; the BOG callback has the per-IP rule of §10.

## 15. Files (ADR-009; foundation operations in `src/paths/f0-files.yaml`)
- Upload: `createFileUpload` (purpose, name, size, type, optional `context`) → presigned POST → client uploads → `completeFileUpload` → scan → `ready` (event `file.processed`). Staff public media: `adminCreateFileUpload`.
- Attach by id: request bodies carry `fileId` / `fileIds` (only `ready` files of the caller with the matching purpose; else `422 FILE_NOT_READY` / `FILE_PURPOSE_MISMATCH`).
- Show: public images as `ImageVariants`; private files as `Attachment`, downloaded by users via `getFileDownload` (404 for non-parties) and by staff via the owner's `/admin/<resource>/{id}/files/{fileId}/download` (§4.2).
- Restricted users (ADR-002 §4) may use `createFileUpload`, `completeFileUpload`, `getFile` and `deleteFile` **only for purpose `appeal_file`** (spec 01 AC-47); any other purpose → `403 ACCOUNT_RESTRICTED` (these four operations have audience `restricted-user` with that note). The purpose and permission checks run **before** a presigned POST is issued, and `completeFileUpload` re-checks the purpose stored on the file (ADR-009 §3, P2-B5 item 12).
- Purposes are the shared `FilePurpose` enum; limits come from the register (S-037…S-040, S-077…S-099) — cite the rows in `x-settings`.

## 19. Rich text (sanitised HTML) — the one sanitiser (SEC-22)
Every field described as "sanitised HTML" or "formatted text" is cleaned by **one server-side allow-list sanitiser** (a single module in `apps/api`, configured from one allow-list file in the shared package `packages/rich-text`, Phase 3). It runs **on every write** and in the **Phase 5 migration ETL** for every legacy HTML value (data-model §12.1). Web and mobile renderers use the same allow-list (web renders only API output; mobile passes the same list to its HTML renderer). Nothing else may render stored HTML.

| Profile | Fields | Allowed elements |
|---|---|---|
| `user_text` | gig description (spec 04 AC-4) | `p`, `br`, `strong`, `b`, `em`, `i`, `ul`, `ol`, `li` |
| `user_text_links` | order details / requirements (spec 06 AC-13, P-48) | `user_text` + `a` |
| `staff_content` | CMS pages and blog articles (spec 17 AC-8, R-C3), category SEO texts `contentTop`/`contentBottom` (spec 03) | `h2`…`h6`, `p`, `br`, `strong`, `b`, `em`, `i`, `ul`, `ol`, `li`, `a`, `table`, `thead`, `tbody`, `tr`, `th`, `td`, `img` |

Rules for every profile:
- Everything not allowed is removed (element kept as text where it wraps text); comments, `script`, `style`, `iframe`, `object`, `embed`, `svg`, `math`, `form`, `input`, `button`, `base`, `meta`, `link` are dropped **with** their content.
- Attributes: only `href` on `a`; `src`, `alt`, `width`, `height` on `img`; `colspan`, `rowspan` on `th`/`td`. No `style`, `class`, `id`, `target`, event handlers (`on*`) or `data-*`.
- `href` schemes: `http`, `https` (plus `mailto` in `staff_content`; relative site paths only in `staff_content`). Anything else (`javascript:`, `data:`, `vbscript:`, protocol-relative `//`) removes the link, keeping its text. URLs are checked after entity decoding and whitespace/control-character stripping.
- `img src` (`staff_content` only) must start with `PUBLIC_MEDIA_BASE_URL` (the public media library); other images are removed.
- Links: links in the `user_*` profiles get `rel="nofollow ugc noopener noreferrer"`; `staff_content` gets `rel="noopener"`. External links in `staff_content` are rewritten to the signed `/redirect` interstitial (spec 17 AC-47); links in user text are rendered through the same interstitial by clients.
- Length and letter rules of the owning spec are checked on the text content after sanitising.
- Tests: an XSS corpus (OWASP cheat-sheet vectors, mutation-XSS cases) runs against the sanitiser and against both renderers in Phase 3.
