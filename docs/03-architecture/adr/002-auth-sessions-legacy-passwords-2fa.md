# ADR-002: Authentication — tokens for web and mobile, legacy bcrypt passwords, email 2FA
Date: 2026-09-28 | Status: proposed

> **Revised 2026-09-28** to match Owner decisions made after P2-B1: Q-082 (2FA trigger is the admin setting S-124 `auth.two_factor.trigger`, default `new_device`, option `new_device_or_ip`) and P-4 as adjusted by the Owner (staff 2FA is the admin toggle S-060, default ON, never hard-coded). Changed: Context, Decision §5, Consequences. The data tables are in `data-model.md` §3.A.

> **Revised 2026-09-30** after the P2-B5 security review (`docs/06-qa/security/00-blueprint-2026-09-30.md`). Changed: §1 every revoked session is deny-listed (SEC-16); §2 host-only prefixed cookie names, exact-origin CSRF rule for every unsafe cookie-capable request, JSON content type, no staff body tokens in production (SEC-14, SEC-15, SEC-17); §3 bcrypt implementation notes (SEC-29); §4 restricted-user wording aligned with the contract (SEC-27) and one referral service (review item 11); §5 per-account cap on wrong codes across challenges and emailed re-authentication codes for accounts without a password (SEC-03, SEC-05 technical part); §6 per-account login counter, throttle on every in-session password or code check, step-up bound to the session (SEC-02, SEC-04); §7 social-login flow bound to the client that started it (SEC-09). The client IP used by every per-IP rule is defined in ADR-013 §14–§19 (SEC-01).

## Context
- Web and mobile must use the same API and the same login rules. Legacy uses Laravel session cookies (`config/auth.php:38-50`), which do not suit a mobile app.
- Vision "must not break": existing users log in with their current passwords. Legacy stores bcrypt hashes, 10 rounds (`config/hashing.php:18,32`, BR-005), PHP prefix `$2y$`. Staff accounts (`admins`) also use bcrypt.
- Legacy bugs: social login ignores banned/pending status (R-020); no user login throttling (R-043); reCAPTCHA optional.
- Owner decisions: email 2FA optional per user with a global admin toggle, code only from a new device/IP (Q-043, Q-063); toggle ON at launch, OFF suspends 2FA for all users and remembers choices (Q-072); staff 2FA is an admin toggle, default ON, never hard-coded (P-4 adjusted, S-060); the 2FA trigger is admin-configurable, default new/unrecognised device (Q-082, S-124); social login keys entered in the admin panel (Q-032); keep restrictions, appeals, IP banning (Q-057).
- Settings: S-052…S-069 and S-124.

## Decision
1. **Tokens.**
   - Access token: JWT signed with Ed25519 (EdDSA), lifetime 15 minutes, claims `sub`, `aud` (`user` | `staff`), `sid` (session id), `iat/exp`. Private key only in the API's `.env`; the public key allows other internal services to verify later.
   - Refresh token: opaque 256-bit random string; only its SHA-256 hash is stored in `sessions` (user, device info, IP, created, last used, expires). Rotated on every refresh. If an already-used refresh token is presented, the whole session family is revoked (theft detection). User refresh lifetime 30 days sliding (spec 01 may tune); staff 12 hours.
   - Revocation: logout, password change or reset, "log out other sessions", session list "revoke", refresh-token reuse (whole family), account deletion, admin ban/restrict/"revoke sessions", staff disable and staff password change or set. **Every** revoked `sid`, whatever the reason, is written to a Redis deny-list with a TTL equal to the access-token lifetime (15 minutes), and every request and socket handshake checks it, so a revoked session stops working at once, not after up to 15 minutes (SEC-16). The Socket.IO gateway disconnects deny-listed sessions (`session.revoked`, realtime.md §2). If Redis is unavailable, authenticated requests fail closed (`503`) rather than skipping the check.
2. **Where tokens live.**
   - Web (`mytask.ge`): `HttpOnly; Secure; SameSite=Lax` cookies set by the API, **host-only (never a `Domain` attribute)** and named with the browser-enforced prefixes (SEC-15): access `__Host-mt_at` (Path `/`), device id `__Host-mt_did` (Path `/`), refresh `__Secure-mt_rt` (Path `/api/v1/auth`; the `__Host-` prefix requires Path `/`, so the refresh cookie uses `__Secure-` and is host-only by omitting `Domain`). Next.js server components read the cookie and call the API with `Authorization: Bearer`.
   - Mobile: `expo-secure-store` (Keychain/Keystore); `Authorization: Bearer`; refresh handled by `packages/api-client` wrapper.
   - Admin (`admin.mytask.ge`): host-only cookies for the `staff` audience: `__Host-mt_staff_at` (Path `/`), `__Host-mt_staff_did` (Path `/`), `__Secure-mt_staff_rt` (Path `/api/v1/admin/auth`). User tokens are never accepted on staff endpoints and vice versa.
   - Local development over `http://localhost`: browsers accept `Secure` and prefixed cookies on `localhost`, so the names do not change. Staging follows ADR-015 §2 (separate registrable domain preferred; otherwise host-only only, no `Domain` anywhere).
   - **CSRF rule (SEC-14), enforced by one global guard, not per operation.** It applies to **every unsafe request** (POST/PUT/PATCH/DELETE) that is not authenticated by `Authorization: Bearer`, i.e. every request that sends or may receive our cookies, **including the public auth operations**: `register`, `login`, `verifyTwoFactorLogin`, `resendTwoFactorCode`, `refreshSession`, `logout`, `startSocialLogin`, `completeSocialLogin`, the password-reset and email-link operations, and their `/admin/auth/*` counterparts. Such a request must (a) carry `X-MyTask-Client` (`web` on the public host, `admin` on the admin host; mobile apps send `ios`/`android` and use Bearer), and (b) if it carries any of our cookies, or `X-MyTask-Client` is `web`/`admin`, or an `Origin` header is present, carry an `Origin` that **exactly equals** the origin of the host it was sent to (`APP_URL` on the public host, `ADMIN_URL` on the admin host; scheme, host and port compared as a string, no suffix or "same-site" matching; `mytask.ge`, `admin.mytask.ge` and `staging.mytask.ge` are same-site, so a same-site check would not be enough). Otherwise `403 CSRF_CHECK_FAILED`. Requests with a body must be `Content-Type: application/json` (else `400 VALIDATION_FAILED`, field code `unsupported_content_type`). The only exception is the RFC 8058 one-click unsubscribe POST (`unsubscribeNotificationEmail`, form-encoded, no cookies read, the signed token is the credential); provider webhooks (`handleBogWebhook`, SendGrid) never read cookies and are verified by their own rules. The empty CORS allow-list (ADR-013 §6) means a cross-origin page cannot send the custom header at all.
   - **Staff tokens in bodies (SEC-17).** In production the admin host is cookie-only: `AdminAuthSession.accessToken` and `refreshToken` are always `null`. Body tokens exist only when `STAFF_BODY_TOKENS_ENABLED=true` (for API tests); the API refuses to start with that flag when `NODE_ENV=production`, and it is never set in the staging or production `.env`.
3. **Legacy password compatibility.** Migrated users keep their hash with `password_algo = 'bcrypt_legacy'`. Login: verify with a maintained bcrypt library after normalising the prefix `$2y$` → `$2b$` (identical algorithm, only the label differs). On success, immediately re-hash the plain password with **Argon2id** (memory 19–64 MiB, parameters tuned for the host) and set `password_algo = 'argon2id'`. The same applies to staff accounts. Users with `password = NULL` (social-only) can log in with their provider or set a password with "forgot password". Legacy sessions/remember tokens are not migrated: every user logs in once after cutover.
   **Implementation notes (SEC-29, tests required in slice 01):** accept the prefixes `$2y$`, `$2a$` and `$2b$` (normalise `$2y$`/`$2a$` to `$2b$` before verifying); bcrypt uses only the first 72 **bytes** of the UTF-8 password (Georgian letters are 3 bytes each), so the legacy verify must pass exactly what PHP hashed (the full string, which bcrypt truncates the same way) and must not pre-hash or reject longer inputs; the Argon2id re-hash uses the full password. An unknown email still runs a dummy Argon2id verify so response times do not reveal which accounts exist (SEC-25). Migrated staff stay disabled until Q-097 is answered.
4. **One login pipeline.** Password login, social login callback, 2FA verification and refresh all end in one `issueSession()` function that checks: account status (active/verified allowed; pending, banned, trashed refused with specific error codes), restriction (restricted users get a normal session, but the API refuses them with `403 ACCOUNT_RESTRICTED` on every operation except those whose contract audience is `restricted-user`: their own account (`getMe`), restriction notices and appeals including `appeal_file` uploads, their notifications, read-only views of their own money (wallet, holds, transactions, payments, payout details, saved cards, withdrawals, points, referrals, subscription, billing profile), push-token removal and logout; `refreshSession` works as for everyone; BR-008, Q-057, SEC-27), IP ban list, and the 2FA requirement. This fixes R-020 by construction.
   **Account activation calls one referral service (review item 11).** The four ways an account becomes active (`register` with S-052 OFF, `verifyEmail`, a new account from `completeSocialLogin`, staff `adminActivateUser`) all call the same `ReferralService.creditSignup(referredUserId)` inside the activation transaction; it posts the points journal with the unique `idempotency_ref = referral:{referredUserId}:signup` (data-model PM-09-01), so a second call is a no-op. No other code path posts referral points. Any future referral cap (SEC-18, Owner question) is added inside this service only.
5. **Email 2FA.**
   - **Who:** a user when S-056 is ON **and** the user switched 2FA on; a staff member when **S-060** `auth.two_factor.staff_required` is ON (Admin Panel toggle, default ON, P-4 as adjusted by the Owner). S-060 is independent of S-056. S-060 OFF means no code for staff.
   - **When a code is asked: setting S-124 `auth.two_factor.trigger`** (Q-082), read at each login, same rule for users and staff:
     - `new_device` (**default**): a code is asked when the device is not trusted, i.e. never confirmed or its trust is older than S-059 days. "Device" = a random device identifier issued by the server (a long-lived secure cookie on web and admin, an install id in SecureStore on mobile), stored only as a hash. A new IP on a trusted device does not ask for a code (mobile networks change IP often); the IP is recorded in the session list.
     - `new_device_or_ip`: a code is also asked when the IP is not yet confirmed for that trusted device within S-059 days.
     - Data: `trusted_devices` plus `trusted_device_ips` (every successful code confirms the device **and** the current IP). Both tables are always written, so the Owner can switch S-124 at any time without data changes; the new value applies from the next login.
   - After a correct password (or social callback, spec 01 AC-30) on an untrusted device/IP: the API answers `202 { challengeId, channel: "email", expiresAt }` and queues an email with a 6-digit code (stored as a hash; TTL S-057 = 10 min; S-058 = 5 wrong attempts invalidate it; resend: 60 s cooldown, at most 5 codes per 15 minutes, spec 01 R-A6).
   - `POST /auth/2fa/verify { challengeId, code }` → tokens + trust for the device (and the IP) for S-059 = 30 days.
   - **Cap across challenges (SEC-03).** S-058 limits wrong codes per challenge, but a caller who knows the password could open new challenges forever. So wrong codes are also counted **per account across all challenges and purposes** (Redis, sliding 1 hour): at **10** wrong codes in one hour, code verification for that account (login, staff login and re-authentication codes) is refused for S-063 minutes with `429 TWO_FACTOR_LOCKED` / `STAFF_TWO_FACTOR_LOCKED` (`details.retryAfterSeconds`), even for a correct code, and the account owner is emailed once per lock ("someone entered your password and then wrong codes"; this email is **NEW** and must be added to spec 15 by the product-analyst before slice 01 ships). For staff, each wrong login code also counts as a failed staff login towards the S-064 IP ban. Both verify operations declare `x-rate-limit` and `429`. The value 10 is a technical constant (not a register row); spec 01 may turn it into one.
   - Switching 2FA on or off needs re-authentication (password, or an email code for social-only accounts, P-15). Switching it off or changing/resetting the password forgets all trusted devices (spec 01 AC-31).
   - **Emailed re-authentication codes for accounts without a password (SEC-05, technical part).** The same challenge (`createMyTwoFactorChallenge`, table `two_factor_challenges`) has the purposes `toggle_two_factor` (P-15), `email_change`, `payout_details` and `revoke_sessions`. An account without a password confirms an email change (`updateMe` with `email`), saving payout details (`putPayoutDetails`) and "log out other sessions" (`revokeMyOtherSessions`) with a code of the matching purpose sent to its **current** address; accounts with a password keep using the password. A code is valid only for its purpose and only once. This replaces "not asked for social-only accounts" in spec 02 AC-29/AC-44 and spec 14 AC-3; the product-analyst records the change in those specs (P2-B5 fixes handoff). Payout cooling periods after such changes are an Owner decision (SEC-05 part 2), not part of this ADR.
   - Toggle OFF (S-056) suspends user 2FA but keeps each user's choice (Q-072); staff are not affected by S-056.
6. **Brute-force protection.** All counters live in Redis; the client IP always comes from the resolver of ADR-013 §14–§19 (SEC-01).
   - **Per account + IP** (spec 01 AC-16): S-062 (5 failures / 15 min) → lock S-063 (15 min) for that account from that IP, with a generic error message (`429 AUTH_LOGIN_LOCKED`).
   - **Per account, any IP (SEC-02).** A second counter per account ignores the IP. When it reaches **20** failed logins within one hour (from any number of IPs), the account enters a **slow mode** for the rest of that hour: at most one password attempt per **30 seconds** is evaluated for that account, others get `429 AUTH_LOGIN_THROTTLED` with `details.retryAfterSeconds`; on web, reCAPTCHA is required for that account's logins while S-061 is ON; the account owner is emailed once per hour (security notice, **NEW**, to be added to spec 15 by the product-analyst). There is **no hard lock**: the real user can still log in during slow mode, so an attacker cannot lock them out. A successful login resets both counters. Values 20 / 1 hour / 30 s are technical constants; spec 01 may turn them into register rows.
   - **Every in-session password or code check (SEC-04).** `updateMe`, `changeMyPassword`, `updateMyTwoFactor`, `revokeMyOtherSessions`, `putPayoutDetails` (users) and `adminReauthenticate`, `adminChangeMyPassword` (staff) share one per-account counter of wrong current passwords and wrong re-authentication codes: S-062 failures within 15 minutes → every further password/code check of that account is refused for S-063 minutes with `429 RATE_LIMITED` (`details.retryAfterSeconds`, messageKey `t_too_many_login_attempts`), even when correct; the failures also count towards the per-account login counter above (so the owner gets the security notice). Wrong codes also count towards the SEC-03 cap. The operations declare `x-rate-limit` and `429`.
   - **Staff.** Staff login keeps the legacy IP-ban rule (S-064 = 3 failures), and wrong staff login codes count as failures (SEC-03). The staff step-up window opened by `adminReauthenticate` is stored against the **session id** (`sid`), not the staff account: another session of the same staff member does not inherit it, and it ends with the session.
   - reCAPTCHA (S-061) verified server-side on web register/login/contact when ON; mobile relies on throttling and may use reCAPTCHA Enterprise / App Check later (spec 01 decides).
7. **Social login.** OAuth 2.0 / OIDC "authorization code + PKCE". Provider client secrets come from the settings register (encrypted, write-only, ADR-005). Mobile uses the system browser (`expo-auth-session`); the API does the code exchange and all provider-token handling. Linking rules follow legacy BR-006 unless spec 01 changes them.
   **The flow is bound to the client that started it (SEC-09; must be in place before any of S-065…S-069 is switched ON).** Presenting `code` + `state` alone never completes a login.
   - `state` is a random 256-bit value, stored hashed in Redis with the provider, the client kind, the redirect URI, the referral code and a 10-minute TTL; it is single-use (deleted at the first callback, successful or not).
   - **Web** (`X-MyTask-Client: web`): the API keeps the PKCE `code_verifier` server-side and, in the `startSocialLogin` response, sets a short-lived binding cookie `__Host-mt_oauth` (HttpOnly, Secure, SameSite=Lax, Path `/`, host-only, Max-Age 600) holding a random nonce whose hash is stored with `state`. `completeSocialLogin` requires that cookie to match the `state`'s nonce, else `422 AUTH_SOCIAL_FAILED`; the cookie is cleared in the response. A callback link crafted by an attacker therefore cannot sign a victim's browser into the attacker's account (login CSRF).
   - **Mobile** (`ios`/`android`): the app creates the PKCE pair itself (`expo-auth-session`), sends only `codeChallenge` (S256) to `startSocialLogin`, keeps `codeVerifier` in memory and sends it to `completeSocialLogin`. The API stores the challenge with `state`, checks `BASE64URL(SHA256(codeVerifier)) = codeChallenge`, and passes the verifier to the provider's token endpoint. Another app that intercepts the redirect has `code` + `state` but not the verifier. The mobile redirect URI is a verified **https App Link / Universal Link** (`https://mytask.ge/app-return/auth/{provider}`, url-map §7), not a custom scheme, wherever the provider allows it.
   - Only provider emails marked verified (`email_verified = true` for OIDC providers; providers that return only verified emails are listed in the adapter) may create or match an account; an unverified email is treated like a missing one (`422 AUTH_SOCIAL_EMAIL_MISSING`, spec 01 AC-41).
8. **Passwords.** Legacy rules kept (8–60 chars, one uppercase, one digit, BR-001); reset tokens single-use, hashed, TTL S-055; password change notifies the user (legacy `PasswordChanged`).

## Alternatives considered
- **Server sessions (cookie) for web + separate tokens for mobile** — two auth systems to secure and test. Rejected.
- **Access and refresh token in `localStorage` on web** — readable by any XSS. Rejected in favour of HttpOnly cookies.
- **Long-lived JWT without refresh** — cannot be revoked. Rejected.
- **Force all users to reset passwords at cutover** — breaks the vision requirement. Rejected.
- **Keep bcrypt forever** — acceptable security, but Argon2id is the current recommendation and the re-hash-on-login costs nothing.
- **Hosted identity (Auth0, Clerk, Cognito)** — monthly cost per user, harder legacy-hash import, data outside our control. Rejected.
- **TOTP (authenticator app) 2FA** — stronger, but the Owner asked for email codes; can be added later as a second method without changing the pipeline.

## Consequences
- Easier: one auth flow for all clients; legacy users notice nothing; banned/pending checks cannot be skipped by any login method.
- Harder: CSRF discipline on cookie-authenticated web requests (enforced centrally in a guard); key management for Ed25519 signing keys (rotation supported with a `kid` header).
- Must change: spec 01 defines exact error codes and UX; data-model.md defines `sessions`, `refresh_tokens`, `trusted_devices`, `trusted_device_ips`, `two_factor_challenges`, `users.password_algo`, `users.locale` (§3.A); security review (P2-B5) checks the token and CSRF design.
- Must change after P2-B5 (product-analyst): spec 01 records the per-account login counter and slow mode (§6), the 2FA cap across challenges (§5) and the throttle on in-session checks; spec 15 adds the two NEW security notices (§5, §6); specs 02 (AC-29, AC-44) and 14 (AC-3) record the emailed code for accounts without a password (§5); spec 01 AC-41 notes that unverified provider emails count as missing (§7).
- Harder (SEC-09): the web social-login callback page must be served on the same host that started the flow (the binding cookie is host-only), and the mobile app must keep the PKCE verifier across the browser round trip.
- Answered (Q-082): the trigger is not fixed in code; it is setting S-124 with the default "new or expired device". A stricter mode (`new_device_or_ip`) is available to the Owner in the Admin Panel. Trade-off documented for the Owner: with `new_device_or_ip`, mobile users on changing networks will be asked for codes often.
