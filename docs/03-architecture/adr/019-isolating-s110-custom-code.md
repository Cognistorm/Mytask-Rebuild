# ADR-019: Isolating S-110 custom code (Phase 3 study P3-9)
Date: 2026-10-01 | Status: **accepted** (Owner 2026-10-01, Q-158 (a)) | Amends: ADR-013 §7 (adds rules, removes none) | Closes: phase-3-plan P3-9, ADR-013 §7 "Phase 3 study"

## Context
- S-110 lets the Super-admin put custom HTML/JS in the head and footer of public web pages (Q-085). The public-page CSP allows the S-127 hosts (ADR-013 §7). Such a script runs on the **same origin** as the cookie-authenticated API, so it can act as the signed-in visitor (SEC-11). The Owner decided Q-146 (c): only fixed-code vendors for now, confirmed per host (spec 16 AC-74a); study isolation in Phase 3. This ADR is that study.
- **What the custom code is used for today.** The live home page (fetched 2026-10-01) renders, from the database custom-code slot (not in the legacy code, `legacy/APP/resources/views/components/layouts/main-app.blade.php:166-168`):
  1. **Google Analytics 4** through the Google tag: `https://www.googletagmanager.com/gtag/js?id=G-…` plus an inline `gtag('config', …)` block.
  2. **Microsoft Clarity** (heatmaps and session recordings): an inline loader that adds `https://www.clarity.ms/tag/<id>`, which then loads `scripts.clarity.ms` and sends data to `*.clarity.ms`.
  Separately, the legacy main layout hard-codes the Facebook SDK and the Messenger customer-chat widget (`main-app.blade.php:210-230`). That is not S-110 and not part of this ADR (see Q-158 note).
- **Facts that shape the answer.**
  - The Google tag is served from `www.googletagmanager.com`, the **same host** as Google Tag Manager containers (`/gtm.js?id=GTM-…`). A GTM container can run any JavaScript an agency types into it; the Google tag (`G-…`) is configured in Google's UI (events, linked Google products) but, as Google documents it, cannot run custom JavaScript. A host-only allow-list (S-127 today) cannot tell them apart.
  - Clarity, by design, reads the **page's own DOM** to record it. In an isolated frame it records an empty frame.
  - GA4 in a frame on another site reports the frame's URL and uses third-party cookies, which Safari and Firefox block and Chrome partitions: visitors are counted again on each visit, so the figures become unreliable.
  - **Client-side navigation defeats "public pages only".** `apps/web` is a Next.js App Router app with one root layout (`apps/web/src/app/[locale]/layout.tsx`). A script loaded on a public page keeps running when the visitor follows a link to `/auth/login`, `/account`, checkout or the inbox, because Next.js swaps the page without loading a new document, and the relaxed CSP of the first document stays in force. Spec 16 AC-73 ("never on auth, account, … pages") is only true if crossing that line loads a new document.

## Options studied
| | Option | Removes SEC-11? | GA4 | Clarity | Cost |
|---|---|---|---|---|---|
| A | **In-page, as now (Q-146 (c)) + hardening below** | No, narrows it (no tag managers, no persistence into private pages) | works | works | small, Phase 4 slice 17 |
| B | **Sandboxed iframe on a separate cookieless registrable domain** (e.g. `mytask-tags.net`), `sandbox="allow-scripts"` without `allow-same-origin`; the page sends a fixed, sanitized event set (`page_view` with path, title, language; never user data) by `postMessage` to the exact frame origin | Yes for frame scripts | counts unreliable (third-party cookies, frame URL) | does not work | medium: second domain, DNS, certificate, Caddy site, static frame page, postMessage bridge, per-vendor adapter, its own CSP |
| C | **Server-side tagging** (GA4 Measurement Protocol, Meta Conversions API) sent by our API, no third-party script in the browser | Yes | works for page views and events the code sends | not possible | medium per vendor; it becomes a feature (spec + contract), not "custom code" |
| D | **Only for signed-out visitors**: the web server renders S-110 only when the request has no user session cookie | Yes for signed-in visitors (the only ones a script can act as) | signed-out traffic only | signed-out only | very small |
| E | **Web worker (Partytown)** | No: the worker reaches the page and the API through a proxy on the same origin | works | partly | small | 
| F | **Drop third-party scripts**, first-party analytics only (ADR-012) | Yes | – | – | none |

E is rejected: it is a performance tool, not isolation. B only pays off for pure pixels and breaks both vendors in use today. C and F are good long-term choices but replace the Owner's tools. D is cheap and strong but loses analytics of signed-in users, which is a business choice.

## Decision (accepted by the Owner 2026-10-01, Q-158 (a))
1. **Keep the in-page model of ADR-013 §7 and Q-146 (c) for launch** (option A). Iframe isolation (B) is **not built** now; its design above is kept here for when a pixel-only vendor is wanted. Options C, D and F stay open to the Owner (Q-158).
2. **Hard boundary between public and private pages (mandatory, web).** `apps/web` gets **two root layouts** in route groups — public (the AC-73 allow-list of routes) and private (auth, account, seller, cart, checkout, payment, inbox, restricted, `app-return`). Next.js loads a new document when navigation crosses root layouts, so a custom script and the relaxed CSP never survive into a private page. Only the public root layout calls `getWebCustomCode` and adds the S-127 hosts to its CSP; the private one always sends the strict CSP. Links between the two are ordinary links; the full reload is the accepted cost. Required E2E test: custom code sets a marker on `window` on a public page; after clicking through to `/auth/login` and to `/account` the marker is gone and the response CSP has no S-127 host.
3. **Built-in deny list (API, code constant, not a setting).** `adminUpdateSetting` refuses S-110 code and S-127 hosts that load a tag-manager container: at least Google Tag Manager (`googletagmanager.com/gtm.js`, `GTM-` container ids), Adobe Launch (`assets.adobedtm.com`), Tealium (`tags.tiqcdn.com`), Segment (`cdn.segment.com`), and the Google Tag Manager server-side preview hosts. The check matches URLs and container ids in the saved code, not only hostnames, so the Google tag (`/gtag/js?id=G-…`) stays possible. Error: new code `422 CUSTOM_CODE_HOST_DENIED` (`details.matches`, messageKey `t_custom_code_host_denied`, NEW en + ka). The list lives in one file with a source comment per entry and is reviewed in the slice 17 security review.
4. **Path-scoped CSP for known vendors.** S-127 stays a list of hostnames (no contract change). For hosts that also serve tag-manager containers, the web server emits a **path-scoped** CSP source from a built-in vendor table instead of the bare host: `https://www.googletagmanager.com/gtag/` (prefix: allows `/gtag/js` and `/gtag/destination`, blocks `/gtm.js`). Other hosts are emitted as listed. Browsers ignore the path after a redirect; the Google tag does not redirect, and the deny list (point 3) still applies to the code.
5. **Session-recording privacy (Clarity and similar).** Public pages show a signed-in visitor's name and avatar in the header. The web adds Clarity's masking attribute `data-clarity-mask="true"` to the header account area (harmless when Clarity is not used), and the go-live checklist asks the Owner to set Clarity masking to "Strict". Whether Clarity may record signed-in visitors at all is part of Q-158 (option D).
6. **Unchanged from ADR-013 §7:** Super-admin only, re-authentication, audit, EV-124, per-host fixed-code confirmation (AC-74a), legacy code imported disabled (AC-75), kill switch S-110 `enabled = false`, never in the mobile app, admin, emails or `getPublicConfig`.
7. **Go-live note (not a rule).** To restore today's tracking after cutover, the Super-admin re-enters the GA4 and Clarity snippets and lists in S-127: `www.googletagmanager.com`, `*.google-analytics.com`, `*.analytics.google.com`, `www.clarity.ms`, `*.clarity.ms` (exact list verified against the vendors' current CSP guides at that time).

## Alternatives considered
See "Options studied". Also rejected:
- **Separate origin for all signed-in pages** (e.g. `app.mytask.ge`) — would isolate cookies from public scripts, but changes every URL, the App Links, SEO and the cookie design of ADR-002. Far too large for the risk.
- **Trusted Types / SRI only** — SRI is already required where vendors allow it (ADR-013 §7); neither stops a trusted vendor script from calling the API.

## Consequences
- Easier: no new domain or infrastructure; today's GA4 and Clarity keep working; the "public pages only" promise (AC-73) becomes true in an app with client-side navigation; tag-manager containers are refused by the system, not only by the Super-admin's tick.
- Harder: two root layouts in `apps/web` (shared header/footer components rendered by both); navigation between public and private pages is a full page load.
- Remaining risk (unchanged from Q-146): a listed vendor, or a compromised Super-admin account, can act as a signed-in visitor on public pages. Option D or C removes it; the Owner decides (Q-158).
- Must change after approval: contract — new error `CUSTOM_CODE_HOST_DENIED` on `adminUpdateSetting` / `adminRestoreSettingVersion` (additive, by the solution-architect); i18n `t_custom_code_host_denied` (en + ka); spec 16 AC-74 gains the deny-list sentence and AC-73 the full-load rule (product-analyst); `apps/web` root layouts and E2E (web engineer, before slice 17 — the split is cheapest now, while few pages exist); API deny-list + tests (backend, slice 17); go-live checklist items (point 5, 7) in Phase 6.
